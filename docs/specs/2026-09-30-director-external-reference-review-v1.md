## Drama Skills 参考审阅（公开 README / 目录）

### Observed

公开 README 明确描述：

1. 项目提供 11 个面向短剧/漫剧的 Agent skills，覆盖原著分析、故事开发、分集剧本、资产、图片提示词、分镜、视频提示词、确认后生产、剪辑和审查。
2. 每集主要维护多份 Markdown 文档，例如剧本、视觉设定、分镜、图片提示词、视频提示词和剪辑单；README 将这些文件描述为创作事实的主要载体。
3. 生产前先预览、确认，再调用外部图片、视频、配音或音乐接口。
4. 角色和跨镜一致性通过文件中的“连续性锁”、镜头引用和确定性检查脚本维护。
5. 公开示例展示了同一镜头在剧本、视觉设定、分镜和视频提示词之间的分层交接。
6. 仓库包含 `evaluations/`、内容质量案例、评分规则和模型行为探针等评估材料。
7. 目录中包含 `short-drama-novel-analyze`、`short-drama-develop`、`short-drama-storyboard` 等分阶段 skill；README 将长材料的分集地图、断点续做和按当前集处理列为工作方式。

### Direct implication

- 该项目把“每层决定的可读文本”作为上下文载体，而不是依赖一个长期模型 conversation。
- 连续性不是一次全局 prompt，而是写入可引用的锁、镜头依据、起止状态和跨文档检查。
- 生产确认和内容生成分离，能避免模型结果直接触发计费任务。
- 评估案例与检查脚本是独立工程资产，说明长流程需要验证“内容交接是否完整”，不能只测 API 是否返回 JSON。

### Not yet proven

- README 和目录索引不能证明其内部是否使用持久化数据库、RAG 或 provider conversation session。
- README 不能证明连续性锁对所有题材和模型都有效，也不能证明样片成本、项目数量或质量指标可迁移到 iframe。
- 未从公开材料确认其分集摘要、关系状态和伏笔追踪的具体 schema 或合并算法。

### 对 iframe 的可借鉴部分

| Drama Skills 做法 | iframe 可采用的等价物 | 采用边界 |
|---|---|---|
| 多份 Markdown 分层交接 | Script / Fact Ledger / Director Interpretation / Director Intent / Shooting Plan 独立 artifact | iframe 使用结构化 JSON + 可读视图，不把所有内容塞进一个长页面 |
| 连续性锁 | `canon_state`、`scene_summaries`、角色/道具状态、source refs、continuity handoff | 每条锁必须能回指 revision 或 source range；不能把模型猜测写成事实 |
| 生产前确认 | 保存草稿 → 用户采用 Director → 预览/确认生成任务 | 用户确认是业务动作，不等同于模型 session 或硬性内容评分 gate |
| 跨文件检查脚本 | Director / shooting plan schema 校验、lineage 校验、story event 引用校验 | 结构错误可阻止；空的创作字段和未知实体应提示并允许继续 |
| 评估案例与行为探针 | Director 验收样例、跨集一致性测试、分片恢复测试、provider 返回/本地状态测试 | 评估结果记录事实，不自动替用户采用模型建议 |
| 当前集优先处理 | Episode Context + bounded Series Context projection | 当前集原文仍是事实来源，系列摘要只做有来源的辅助上下文 |

### iframe 与 Drama Skills 的关键差异

1. **存储形态**：Drama Skills 以项目目录和 Markdown 文件作为主要工作面；iframe 以服务端结构化 artifact、revision、job 和 API-key scoped workspace 作为权威存储。
2. **导演理解位置**：iframe 明确把 Director 理解放在剧本解析之后、导演意图和拍摄计划之前，并要求用户保存/采用；Drama Skills README 更强调从故事开发直接交接到分集剧本、资产和分镜文件。
3. **事实与解释分层**：iframe 需要区分原文事实、Director interpretation、用户决定、假设和 unresolved；Markdown 文件本身不自动提供这些状态语义，需要额外元数据或检查规则。
4. **任务恢复**：iframe 有 owner、generation attempt、批次、lineage 和 provider 任务状态；Drama Skills 的公开材料更强调文件和 CLI 工作流，不能据此推断相同的异步任务模型。
5. **用户界面**：iframe 必须把结构化数据变成可视化时间线、关系图、故事线和 Director 编辑视图；Markdown 是可审计交接格式，但不能替代图形交互。

### 对 Director 设计的新增建议

从该仓库可以增加一条明确原则：

> 每个 Director 决定都应有一个可读、可引用、可检查的“交接面”，而不是只存在于 prompt 或模型返回 JSON 中。

在 iframe 中，这个交接面可以是：

- Director 理解：事件、人物关系、时间线、故事线和待决问题；
- Director 意图：视觉/表演/声音/节奏和连续性锁；
- 拍摄计划：场景、节拍、镜头以及每镜的来源和状态；
- Review findings：每个问题的证据、严重程度、建议动作和用户决定。

每次生成或局部修订都应保留可读摘要和 machine-readable payload；二者必须由同一个 revision 产生，不能让 UI 展示一套文本、下游 prompt 使用另一套隐藏数据。

## 用户提供的多 Agent 方案摘录

摘录描述了四类 Agent：

1. **知识图谱架构师**：多格式解析、实体抽取、人物档案、事件链、关系网和时空坐标，并以向量与图结构保存信息。
2. **编剧老师**：使用风格、时长、受众等配置进行大纲和分集规划，结合人物个性化记忆创作台词，并通过 RAG 约束原著还原。

4. **视觉导演**：把动作描述转换为镜头术语，补充光影、材质、色调等视觉指导，并输出多模态模型 Prompt。

## 对 iframe Director 的直接启示

### 1. 关系图应有范围和筛选

Director 的人物关系图可以增加以下只读筛选：

- 当前阶段 / 全部阶段；
- 当前事件涉及人物；
- 关系状态变化；
- 只显示有事件触发的关系；
- 角色出现次数或关系强度阈值。

筛选只改变视图，不创建新的 Director 草稿，也不改变确认版本。编辑仍写入同一个 `story_map`。

### 2. 关系演化应与时间线共享事件锚点

关系图中的边应能够显示：

- 起始阶段；
- 发生变化的事件；
- 当前关系状态；
- 变化前后摘要。

这与 iframe 已有 `relationship_arcs[].states[].trigger_event_ids` 数据结构一致，是对现有结构的视图增强，而不是新增一套关系状态。

### 3. 长任务恢复应保持现有 job lineage

参考项目的暂停、继续、切片重试和刷新恢复，与 iframe Director 的 profile/shooting-plan job 模式方向一致。可借鉴的 UI 信息是：

- 本地 task ID；
- 上游 provider task ID（若已返回）；
- 当前切片 / 总切片；
- 最近更新时间；
- 失败切片和“从未完成段继续”。

这不改变 Director 草稿、确认和拍摄计划的状态边界。任务恢复只能继续同一 generation attempt，不能偷偷覆盖已确认 revision。

### 4. 图谱、记忆、审核和视觉导演应拆成不同边界

用户提供的四 Agent 架构与 iframe 当前产品可以形成以下映射：

| 外部能力 | iframe 对应边界 | 可以借鉴 | 不应直接等同 |
| --- | --- | --- | --- |
| 知识图谱架构师 | 剧本解析、`ScriptFactLedger`、Director `story_map` | 实体、事件、关系和时空坐标的结构化索引 | GraphRAG 或向量库不是现有事实；不能把模型推断写成原文事实 |
| 编剧老师 | 当前不属于 Director；属于未来剧本创作/改编模块 | 风格、时长、受众等显式配置 | 不应让 Director 自动重写剧本原文 |
| 审核专家 | Director diff、连续性审阅、拍摄计划检查 | 多维检查和可解释修改建议 | 评分不能成为未经用户同意的硬 gate |
| 视觉导演 | Director 意图和 shooting plan | 镜头术语、视觉锚点、光影与声音建议 | 建议必须标注为导演意图或可选补充，不能冒充剧本事实 |

这张映射支持一个重要边界：Director 是“理解 → 意图 → 拍摄计划”的审阅与决策工作面，不是四个 Agent 的混合聊天窗口。各类分析可以协作，但产物必须回到明确的 revision、diff 和用户采用动作。

## 对 iframe 的可执行设计启示

### A. 图谱层：先做来源可追溯的结构化索引

人物、地点、道具、事件和时间锚点可以作为 `story_map` 的节点或引用，但每个节点需要区分：

- 原文明确内容；
- Director 对原文的解释；
- 导演主动补充的视觉锚点；
- 尚未决定的问题。

图谱视图的作用是帮助用户发现时间、关系、场景和情绪上的缺口。它不能因为图谱中存在节点，就证明剧本写过该节点。

### B. 记忆层：采用可检索的 Director revision，而不是隐藏记忆

人物性格摘要、关系变化、连续性状态和导演风格可以保存为带名称、版本摘要、revision、来源和更新时间的记录。下游生成只读取最近一次“采用”的 Director revision；草稿和未采用建议不进入模型上下文。

这与用户已经确认的“用户命名 + 版本摘要 + 可检索标题”一致，也比把长期记忆隐式塞进 prompt 更容易回溯。

### C. 审核层：建议与 gate 分离

审核可以输出结构完整性、来源覆盖、关系连续性、场景可执行性和资源引用等检查结果，并给出修订建议。默认行为应是：

- 空的环境声、灯光、对白等创作字段：提示补充，不阻止保存；
- 未知角色、道具或场景 ID：记录为 unresolved reference，不拒绝整份计划；
- 需要用户决定的时代、地点和视觉锚点：进入导演问题或导演意图草稿；
- 只有真正无法解析的结构错误才阻止提交，并给出可修复字段。

审核结果必须说明证据和直接动作，不能只显示一个总分。

### D. 视觉导演层：把可选加工落在拍摄计划

例如“学校所在地为西安”可以生成回民街、钟鼓楼、街巷等视觉锚点建议；这些建议的状态应是“导演补充 / 可选建立镜头”。它们只有在用户采用 Director 意图或拍摄计划草稿后，才进入下游镜头生成。

原剧本未出现的地点、道具、对白和动作不能写入剧本原文，也不能伪装成剧本事实。

## 不应直接引入的内容

1. **章节模型**：参考项目面向小说/剧本章节；Director 当前以 `phase → event → scene → beat → shot` 为核心，不应把章节直接当成拍摄场景。
2. **关系强度替代导演判断**：出现次数或统计强度只能作为筛选提示，不能自动修改人物关系或生成剧本事实。
3. **异名自动合并**：只能生成候选合并，必须保留原名、来源和用户决定；时期变体不能因为字符串相似而强行合并。
4. **本地 SQLite 假设**：iframe 使用 API key 识别工作区并由服务端持久化，不能把浏览器本地存储当作跨浏览器恢复的主来源。
5. **图形库替换**：README 只证明参考项目使用 G6，不证明 iframe 需要替换当前图布局。先验证现有 SVG/节点交互是否满足筛选、展开和编辑需求。
6. **“审核专家”自动重写**：外部方案描述了低分后触发优化，但 iframe 必须保留用户决定权；审核只能产出候选 patch。
7. **“个性化记忆”直接注入模型**：没有 revision、来源和采用状态的隐式记忆会破坏 Director diff 和回溯。
8. **把视觉导演建议当作原作事实**：视觉锚点、镜头术语和色彩建议归属于导演意图或拍摄计划。

## 与当前 Director 三层流程的关系

```text
剧本原文
  ↓
导演理解：时间线、事件、人物和关系演化（可审阅、可修订）
  ↓
导演意图：视觉、表演、声音、节奏和连续性（可修订）
  ↓
拍摄计划：scene → beat → shot（独立草稿）
```

外部项目的关系图和筛选属于“导演理解”的可视化辅助；暂停/继续属于分析任务基础设施；二者都不新增事实确认闸门，也不改变“保存草稿”和“采用当前 Director 理解”的边界。

### P1：拆分“叙事场景、拍摄场次、分镜镜头”的术语

当前产品把 `scene` 用在不同层级，必须先拆开含义：

| 用户术语 | 所在层 | 含义 | 是否必须 |
| --- | --- | --- | --- |
| 叙事场景 / 原作场景 | 导演理解 | 剧本中一个连续的地点、时间和行动单元；用于判断场景边界 | 每个事件至少有一个归属或候选归属 |
| 拍摄场次 | 拍摄计划 | 为执行而组织的一组连续场景内容，可因调度、地点或制作安排合并/拆分 | 每个 beat 属于一个拍摄场次 |
| 分镜镜头 | Storyboard | 一个具体画面/机位/动作单元 | 每个镜头必须属于一个拍摄场次和 beat |
| Assets 场景实体 | Assets | 可复用的地点视觉资产，如“西安回民街夜景” | 可选；没有资产时允许 unresolved scene reference |

因此，Director 中的“场景分析”不是可有可无的摘要卡片，而是从剧本理解到拍摄计划的连接层：

```text
剧本事实 / 事件
  → 叙事场景（story scene）
  → 拍摄场次（plan scene）
  → 戏剧节拍（beat）
  → 分镜镜头（frame / shot）
```

边界规则：

- 每个事件至少绑定一个**叙事场景候选**；一个叙事场景可以包含多个事件。
- 一个事件跨越地点或时间切换时，拆成多个叙事场景引用，不能用一个无边界摘要掩盖切换。
- 每个 beat 和镜头必须属于一个**拍摄场次**；拍摄场次可以由一个或多个叙事场景组成，也可以为制作调度拆分。
- 每个拍摄场次至少包含稳定 `scene_id`、场次标识/标题、地点、时间锚点、入场状态和出场状态。
- Storyboard 的每个 frame/shot 必须有 `scene_id` 和 `beat_id`；这个 `scene_id` 指向拍摄计划场次，不代表它自动等于原作叙事场景。
- Assets 中的场景实体 ID 是资源引用，不是叙事场景或拍摄场次身份；实体不存在时记录 unresolved reference，不拒绝整份计划。
- “场景分析”负责确认叙事场景边界、与拍摄场次的映射和连续性；它不是剧本事实，也不自动新增剧本内容。
- 旧版只有 `timeline` 或 `key_events` 时，系统可以提供“待整理场景候选”，但必须标记为候选并由用户采用；不能把关键事件直接伪装成已确认场景。

当前 `scene_summaries` 是兼容旧 Director 输出的自由数组，尚不足以表达事件、beat、shot 的稳定引用。后续应在 `story_map` 增加叙事场景节点及事件到场景的引用，再由拍摄计划生成独立的拍摄场次 `scene_id`；Storyboard frame 继续引用拍摄场次 ID，并通过 `story_event_ids` 保留原作事件来源。
