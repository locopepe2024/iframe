# 小安：能力目录、动态卡片与统一任务上下文 v1

日期：2026-10-29  
状态：设计待验证；本文不表示相关协议已实现或部署。  
关联：[现有任务与工具协调切片](2026-10-29-companion-agent-tool-coordination.md)

## 1. 目标与边界

小安是用户的个人助理。用户可以说话、打字或点击卡片，小安理解当前操作对象，调用相册、日记、创作等工具，并根据真实结果继续交流。

本设计解决的核心问题：用户说“修改一张照片”是在开启操作，不等于提供图片提示词；接着说“从相册选”是在推进同一任务，不应新建冲突任务。后续增加功能应主要补充能力定义、工具和必要组件，减少针对每种说法扩充路由条件。

首个验证范围仅为：**开启图片编辑 → 选择素材来源 → 上传或相册选图 → 补充修改要求 → 展示待核对设置**。不在本切片提交付费生成，不改造实时语音传输，不一次性重写所有相册和日记页面。

假设：继续使用现有 React 卡片、服务端任务存储、UniArt Qwen 和 OpenTalking。此设计并不依赖新增端侧模型或 GPU。

## 2. 已观察事实与待验证判断

### 代码事实

- `src/apps/companion_runtime/tools.py` 已有严格参数模型、能力分组及工具 schema，可继续作为能力目录的基础。
- `model.py` 当前请求云端 Qwen 返回文字或一个工具调用，没有多步工具循环。
- 图片任务已有 task ID、revision、阶段和素材绑定；更新工具已包含 `open_upload`、`open_album`。
- `MediaDraftCard.tsx` 使用固定 React 布局和素材来源按钮，尚无通用声明式卡片协议。
- 主机协调器目前提供只读建议；服务端持久化状态才是执行依据。OpenTalking 播放主 Agent 结果，不应独立规划业务操作。

### 直接推论

已有工具和任务模型支持做小范围协议验证，无须先引入完整生成式 UI 框架。仅让模型知道工具名称还不够，必须同时提供当前焦点、允许动作和执行回执。

### 尚未证明

“能力目录 + 任务快照”能否让真实 Qwen 稳定理解连续改口、来源选择及跨任务切换，尚需多轮实测。JSON 校验只能证明结构合法，不能证明理解正确。网页播放事件也不能证明用户实际听到了声音。

### 设计假设

受限的动态卡片能够降低固定路由复杂度，并使点击、文字和语音的结果更一致。以第 10 节的对照用例验证，不以框架名称或 schema 的存在作为成效依据。

## 3. 分工：一个业务语境，多种输入输出

```text
文字 / 语音转写 / 卡片点击
           ↓
会话入口：生成事件、绑定当前任务与焦点
           ↓
自然语言 → Qwen 提议工具或澄清问题
卡片点击 → 已注册动作（明确参数时直接执行）
           ↓
服务端：归属、版本、前置条件、确认和幂等校验
           ↓
执行工具 → 持久化结果 → 生成回执与下一步卡片
           ↓
消息流 / 当前工作卡片 / OpenTalking 播放同一份回复
```

| 层 | 职责 | 状态边界 |
|---|---|---|
| Qwen | 理解意图、提取明确参数、选择工具、提出一个必要问题 | 只能提议，不能宣布未执行操作成功 |
| 主机/端侧协调器 | 可选的焦点和任务建议 | 不单独执行，不保存第二份业务真相 |
| 服务端运行时 | 工具注册、校验、执行、任务状态、结果日志 | 唯一业务状态写入方 |
| 前端 | 渲染注册组件、收集选择、报告界面事件 | 持有临时 UI 状态，不推断业务成功 |
| OpenTalking | 播放本轮回复、处理播放与打断 | 不再生成第二份业务答复 |

v1 每轮最多执行一个业务工具，完成后返回一个用户可理解的下一步。下一步依赖用户输入时立即等待，不在后台连续创建任务。

## 4. 三份目录与统一快照

### 4.1 能力与工具目录

以现有 Pydantic schema 为参数定义来源，增加以下可检索元数据，避免手写两份参数类型：

| 字段 | 含义 |
|---|---|
| `name` / `version` | 稳定工具标识和契约版本 |
| `description` | 能做什么、不能做什么、何时需要澄清 |
| `input_schema` / `output_schema` | 输入参数与真实结果结构 |
| `preconditions` | 所需任务类型、阶段、素材等 |
| `effect` | 只读、导航、草稿更新、保存、删除或付费提交 |
| `confirmation` | 无需确认、明确用户指令、预览后确认等既有业务规则 |
| `ui_actions` | 可以触发此能力的注册卡片动作 |

工具目录按当前焦点提供相关子集，保留切换任务入口。不能因缩减目录而让模型误称“没有相册能力”。v1 子集范围和长度记录在调试日志中，先不引入复杂检索器。

### 4.2 卡片组件目录

首片只新增 `choice_card`：标题、可选说明、少量选项。继续复用上传卡片、相册选择器和创作设置卡片。

模型可以选择组件、组织简短文字、从注册动作中选择选项；服务端绑定真实任务和可用动作。禁止生成可执行代码、任意接口地址、任意布局或虚构素材 ID。

图片编辑的来源卡固定支持“上传照片”“从相册选择”“返回聊天”。语义明确时可直接打开相应入口，不要求每次先展示来源卡。后续卡片类型经验证再扩展。

### 4.3 状态与回执目录

模型输入快照由服务端组装，包括：会话时间与时区、近期对话及必要摘要、当前任务 ID/revision/阶段、已选素材、当前编辑焦点、待确认动作、允许工具、最近操作回执。

保留其他任务的简短引用，避免为了编辑照片忘记用户正在写日记；不要默认发送全库照片、全部历史或全部记忆。查询日记、历史和记忆仍使用各自工具。

焦点至少区分 `chat`、`media_draft`、`photo_detail`、`diary_editor`、`album_picker`。焦点附带对象 ID 和版本，不以页面可见即认定用户仍要继续该任务。写日记时提到“照片”“视频”默认作为日记内容；只有明确操作意图才切换，歧义时询问一次。

## 5. 声明式卡片协议草案

以下为自定义协议草案，**不是 A2UI 或 JSON Render 的兼容性声明**。示例为服务端校验后的输出，ID、版本及动作绑定不是模型自由填写的内容。

```json
{
  "protocol": "companion.ui.v1",
  "card_id": "card_123",
  "task": {"id": "task_123", "revision": 1},
  "component": "choice_card",
  "status": "active",
  "props": {
    "title": "想修改哪张照片？",
    "options": [
      {"id": "upload", "label": "上传照片", "action": "media.open_upload"},
      {"id": "album", "label": "从相册选择", "action": "media.open_album"},
      {"id": "back", "label": "返回聊天", "action": "media.pause"}
    ]
  },
  "spoken_text": "想修改哪张照片？可以上传，也可以从相册选。"
}
```

点击事件携带 `card_id`、`option_id`、任务 ID/revision 及本次 `operation_id`。服务端根据已保存卡片解析动作，不能直接执行客户端任意传入的工具名。自然语言回答经 Qwen 提议后，进入同一业务工具执行器。

卡片有 `active`、`resolved`、`superseded` 状态。旧卡留在消息历史但不反复弹窗；刷新或翻历史不重新执行导航。过期卡提示使用当前任务，不能覆盖新任务。

导航分开记录：`requested` 表示请求打开，`displayed` 表示前端实际展示，`failed` 表示未能展示。尚无展示回执时回复“请在卡片里选择照片”，不要说“相册已打开”。`displayed` 也不代表已经选图、上传或保存。

## 6. 首个交互流程

| 用户输入或事件 | 系统行为 | 应保留的状态 |
|---|---|---|
| “我们修改一张照片吧” | 创建无 brief 的图片编辑任务，展示来源卡 | 等待素材，不能把启动句写成提示词 |
| “嗯，修改照片” | 继续同类活动任务，说明当前待选照片 | 同一 task ID，不报冲突、不重复创建 |
| “从相册里选”或点击选项 | 请求打开同一个任务的相册选择器 | 保留 brief 和已选条件 |
| “上传”或点击选项 | 展示上传卡片；用户点击选择本地文件 | 不声称能仅凭语音打开系统文件选择器 |
| 选中文件，尚未上传 | 展示本地缩略图与待确认状态 | 本地选择不等于相册已保存 |
| 上传成功或从相册选中 | 用真实素材 ID 绑定任务，问“想怎么修改？” | 更新版本；标记来源卡已处理 |
| “把背景换成海边，人不变” | 写入具体修改要求，展示待核对设置 | 保留人物不变约束 |
| “换另一张” | 回到选图，保留可继续使用的修改要求 | 替换素材前核对当前任务版本 |
| “先不改了，聊会儿” | 暂停并保留草稿，回聊天 | 不取消、不提交生成 |
| “改成做视频” | 询问或按明确要求切换任务，暂停原草稿 | 不擅自继承不适用参数 |

若首句已包含真实画面要求，应保存用户明确要求，并仅补问缺少的素材等必要条件，不强制重走全部步骤。输入工具参数合法但语义不完整时，继续询问，而不是填默认内容直接进入生成。

## 7. 一致性、失败与语音

- 同一任务的业务修改串行执行，并使用 expected revision；点击与语音并发时不盲目重放过期参数。服务端重新读取状态，明确下一步。
- 网络重试复用原 operation ID；用户新的一次选择使用新 ID。同一操作重复提交不得重复创建草稿或重复绑定素材。
- 上传失败不进入已选素材阶段；用户原话、已上传素材及现有草稿保留。重试仅重试失败操作，不重启整段对话。
- 本轮业务回复只有一个来源：工具失败不读成功话术；工具成功后，消息文字和 OpenTalking 使用同一回执。播放失败不撤销已保存操作，不再次执行业务工具。
- 打断只停止当前播放，不取消业务任务或断开整段会话；任务取消需要独立明确操作。听与说保持独立状态及队列，并关联 turn ID，避免旧回复抢占新任务。

## 8. 能力缺口记录

工具目录没有所需能力时，可提出 `capability_gap` 记录：来源消息 ID、当前任务/阶段、希望完成的动作、缺少的输入输出、可用替代步骤。服务端按用户与规范化能力标识归并，保留来源和次数；无法确定是否重复时保留待归并状态，不只依赖文案相等。

鉴权失败、超时、版本冲突、参数错误属于运行失败，不自动归类为缺工具。模型判断不足以证明能力确实缺失，记录需标注“待开发核对”。不能由模型即时创建接口或伪装执行成功。

本项为后续独立切片，不是首个动态卡片验证的前置条件。

## 9. 技术选型与实施顺序

参考方向：A2UI 的可信组件目录、JSON Render 的 schema/registry、CopilotKit 的共享状态、AG-UI 的事件流。参考项目的存在不证明适合当前系统；接入版本、兼容性和依赖成本需另行核实。

1. **设计走查**：核对本文交互和样例，明确卡片字段及任务归属。当前仅完成这一步的文档草案。
2. **后端窄切片**：从现有工具 schema 生成目录；定义来源卡提议及校验；复用草稿执行器和回执。
3. **前端窄切片**：实现注册 choice renderer，复用相册/上传组件；接入卡片事件和生命周期。
4. **模型与语音验证**：真实 Qwen 理解测试；再验证文字回执与 OpenTalking 同步。
5. **扩展决策**：确认收益后扩展相册、日记、缺口记录；评估是否引入 JSON Render/CopilotKit。首片不新增上述框架依赖。

预期影响路径：`src/apps/companion_runtime/{tools,model,chat_store,media_drafts,api}.py`、新增卡片协议模块；`frontend/src/lib/companionApi.ts`、`frontend/src/components/companion/agent/{AgentChat,MediaDraftCard}.tsx`、新增注册渲染组件及对应测试。以实现时实际差异为准，不借此开展无关清理。

## 10. 验证与通过条件

### A. 确定性测试

覆盖启动句不变成 brief、同类重复启动继续任务、点击/工具选择来源得到相同业务状态、未知组件/动作拒绝、跨用户及跨任务 ID 拒绝、版本过期不覆盖、重试幂等、历史卡不自动弹窗、上传失败保留草稿、导航回执与业务回执区分。

这些测试须全部通过。建议命令：

```bash
pytest -q -p no:nose tests/test_companion_media_drafts.py tests/test_companion_chat.py tests/test_companion_services.py
cd frontend
npm run typecheck
npm run test:ui -- --run src/components/companion/agent/MediaDraftCard.test.tsx src/components/companion/agent/AgentChat.test.tsx src/components/companion/agent/OpenTalkingReply.test.tsx
```

实现时补入新增协议/renderer 测试；上述命令不表示新功能已经经过测试。

### B. 真实 Qwen 多轮测试

固定模型、目录及 prompt 版本，至少 20 组多轮场景、每组重复 3 次，并保留当前版本对照。覆盖口语重复、改口、已有选图、来源切换、日记中提及照片、明确切换任务、失败重试及缺少工具。

记录每轮期望动作、实际工具、任务 ID、brief、澄清次数、延迟及费用。建议初始门槛：任务/来源选择正确率至少 95%；不把纯启动句写成 brief；不虚报上传、保存或生成成功。后两类错误任一次出现即阻止扩展测试。门槛为设计目标，当前没有实测结论。

### C. 浏览器与自然语音测试

在当前 Mac Chrome 及移动尺寸模拟下完成上传和相册两条路径；同一场景分别用点击、文字和自然语音走一遍。检查缩略图、焦点、卡片更新、返回、刷新恢复，以及“文字显示的结果就是小安说的结果”。实际发声由人工确认，不能以播放事件代替。

## 11. 本次设计建议

保留聊天为唯一主入口，以注册卡片承接具体操作。模型负责理解与提议，服务端负责状态与执行，前端负责可控呈现，语音负责表达同一个结果。

先验证一条图片编辑链路，再迁移其他工作域。只有真实理解和跨输入一致性达到门槛，才扩大动态卡片覆盖范围。

## 12. 第一切片实现记录（2026-10-29）

已实现并在本地验证：

- `ui_cards.py` 定义来源卡目录、模型可提供的标题 schema 和服务端固定的三个动作；`tool_schemas()` 暴露对应目录。模型通过启动工具的 `source_choice` 参数提供标题，省略时采用默认标题。
- 来源卡从当前任务派生，绑定 task ID/revision。点击携带 card ID、option ID 和 operation ID，服务端解析后复用草稿更新执行器；自然语言仍由 Qwen 调用已有工具。
- React `ChoiceCard` 只渲染注册选项，使用原生按钮和 fieldset；按钮至少 44px 高，纵向布局、8px 间隔。失败后仅提供原选择重试，复用原 operation ID。
- 相册导航按事件 ID 防止同一次回执在重绘时再次弹窗。上传来源确认后，用户仍需点击本地文件选择按钮。选择真实素材后，来源卡不再出现。
- 37 项后端测试、60 项 UI 测试通过，前端类型检查和 `/companion-demo` 静态构建通过。构建沿用现有静态导出配置，rewrites 由部署网关处理。

明确未实现或未验证：通用卡片编排、模型自由组合选项、持久化的卡片历史生命周期、前端 `displayed` 导航回执、自动能力缺口归并，以及真实 Qwen 60 次多轮试验。本片导航话术已避免提前宣称界面打开。没有新增完整生成式 UI 框架依赖，也没有改动 OpenTalking 传输。

本地测试使用了工作区已有的其他 Companion 修改，不能据此宣称干净提交独立构建通过。尚未部署此次切片；下一步先执行真实模型语义用例，再在测试站验证自然语音、手机尺寸和实际发声。
