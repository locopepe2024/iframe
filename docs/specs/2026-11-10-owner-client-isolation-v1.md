# Owner credential isolation

GreenA runtime inspection found two active workspaces resolving the same New One token, with and without its `sk-` presentation prefix. One workspace's encrypted credential had been replaced with the server test credential during an earlier 401 repair. The shared-provider credential opt-in was also enabled. This establishes a configuration error; it does not establish that concurrent client reuse caused the recorded requests.

Remediate only the workspace whose saved key differs from its identity and matches that shared token. Back up the encrypted user configuration, remove that credential, and disable shared credential fallback in the deployed environment. Preserve projects, histories, model settings, other owners and upstream channel credentials. Do not substitute another user's token or modify billing history. The affected user must enter their own valid GreenA key. Runtime comparisons must keep raw keys in memory and print only opaque workspace labels and equality results.

The shared LLM adapter also updates its cached client and credential identity in separate mutable fields. An interleaved cache hit can return a client replaced by another owner after comparing credentials. Replace the pair with one immutable cache entry, snapshot it locally, and return the client from that snapshot or from the local constructor result. Preserve desktop caching and explicit per-gateway credential resolution.

Verify an interleaved two-owner request at a cache hit, distinct request Authorization at the HTTP transport boundary, credential rotation, missing-key rejection with shared fallback disabled, and existing LLM/Agent/image/video gateway routing tests. Use an isolated deployment candidate; block cutover while user jobs are active. Verify encrypted configuration changes are confined to the affected owner and existing screenplay/project/library files remain unchanged. Do not perform paid provider generations to prove credential separation.
