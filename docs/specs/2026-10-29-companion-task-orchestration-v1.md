状态：目标架构设计；原子计划提议器已有隔离实验，持久化编排执行器尚未实现。2026-10-29。

承接 [来源卡设计](2026-10-29-companion-declarative-cards-and-tools-v1.md) 与 [真实模型验证](../agents/deliverables/2026-10-29-companion-source-card-live-validation.md)。

## 问题证据

真实模型曾在 `open_album` 动作中携带修改要求。当前执行器只执行导航，不保存同次调用的 brief。单个更新工具同时暴露导航、选图和要求修改，结构校验没有识别这种动作与字段冲突。这是已观察到的契约问题；等待选图的上下文是否促使模型重复导航，仍需对照验证。

只拆工具名称不能解决一个请求涉及多个步骤的问题，因此同时引入服务端任务编排。模型负责理解并提出计划，执行器负责依赖、版本、权限、暂停点与实际回执。

## 原子工具

以下是拟定接口，参数最终由严格 schema 定义，不接受无关字段。

| 工具 | 输入 | 效果 |
|---|---|---|
| `media.task.ensure` | 类型、可选当前任务引用 | 创建任务或取得当前同类任务，不覆盖已有要求 |
| `media.brief.set` | 任务引用、完整修改要求 | 独立保存要求；不依赖选图完成，不打开界面 |
| `media.source.request` | 任务引用、来源 upload/album/ask | 生成来源或选图卡片；不绑定素材、不写要求 |
| `media.asset.bind` | 任务引用、槽位、已验证素材引用 | 绑定上传或相册选择产生的真实素材 |
| `media.task.pause` | 任务引用 | 暂停并保留草稿 |
| `media.task.cancel` | 任务引用 | 明确取消任务 |

参数设置、生成预览与付费提交继续复用既有能力；后续逐项原子化。本片不改变图片/视频模式支持范围。按钮专用事件不暴露给模型。

`brief.set` 是替换完整要求，模型须保留此前未被撤销的约束；歧义时询问，不能猜测。运行时对不匹配动作的参数直接拒绝，不能默默忽略。

## 任务与计划分层

任务保存长期业务状态：类型、要求、素材、设置和版本。计划记录一次用户请求如何推进任务，不复制一份业务状态。

计划包含 `plan_id`、源消息 ID、任务绑定、步骤、依赖、状态和回执。步骤只引用注册工具，任务引用由服务端绑定当前真实任务；用户明确切换任务需单独处理，不能让模型任填其他任务 ID。

步骤状态：`pending`、`running`、`waiting_user`、`succeeded`、`failed`、`cancelled`。计划可处于执行、等待、失败、完成或取消状态。界面焦点是输入，不是执行成功证明。

示例：“修改一张照片，把背景换成海边，人物不变，从相册选。”

```json
{
  "steps": [
    {"id":"task","tool":"media.task.ensure","arguments":{"type":"image_edit"},"depends_on":[]},
    {"id":"brief","tool":"media.brief.set","task_from":"task","arguments":{"brief":"背景换成海边，人物保持不变"},"depends_on":["task"]},
    {"id":"source","tool":"media.source.request","task_from":"task","arguments":{"source":"album"},"depends_on":["brief"]}
  ]
}
```

该示例为提议格式，不是已上线 API。服务端验证无环依赖、工具允许列表及参数；限制为最多 4 步、串行执行、每轮至多一个等待用户步骤且必须在末尾。禁止任意对象路径插值；`task_from` 只能引用前置 ensure 的任务结果。

来源步骤发出卡片后进入 `waiting_user`；浏览器展示只更新界面回执，真实上传或选图完成才产生素材事件。素材事件执行 `asset.bind` 后结束该等待，不自动提交生成。用户只说了修改要求时，先存要求，再由任务缺项决定询问素材；不能因素材缺失丢弃要求。

## 编排执行规则

1. 校验整个提议的结构、依赖和工具可用性，再开始执行。每步运行前仍检查业务前置条件。
2. 同一任务串行写入。模型给出计划时绑定初始版本；计划内后续步骤使用上一成功步骤的真实版本。外部并发修改引发冲突时停止，不静默重基或重新解释用户原话。
3. 每步使用稳定的 `plan_id + step_id` 幂等键。网络重试读取已完成回执，不再次创建任务、上传或提交生成。
4. 每步事务提交业务变化和执行回执。前步成功、后步失败时保留已保存要求；计划明确标注部分完成，不把整个请求报成功，也不回滚用户已确认事实。
5. 崩溃恢复从持久化回执继续；不能确认外部副作用的步骤先对账，不能盲重试。第一片仅允许本地草稿变更与卡片请求，不编排外部付费副作用。
6. 等待用户期间释放执行锁。用户改口触发计划修订或暂停，旧卡不能推进新版本。等待状态不得后台重复调用模型。
7. 删除、覆盖、外部分析及付费操作保持各自既有确认规则；计划批准不等于用户批准所有副作用。

## 模型与表达

首片一次模型调用提出有界计划，不引入无限工具循环或第二个自主业务 Agent。计划执行器无语义判断，不通过关键词猜意图。

工具目录包含前置条件、输入和结果 schema；模型上下文包含当前任务、允许能力、用户原话及最近回执。具体任务 ID/版本仍由服务端限定。

编排回执生成一份消息和下一步卡片。例如：“修改要求记下了，请选一张照片。”OpenTalking 播放同一份文本；模型不得另说已完成修图。失败时明确哪个步骤完成、哪个未完成，不向用户展示工具协议文本。

## 迁移与验证

先为图片编辑新增上述窄接口和单任务计划执行器，内部复用已验证的任务存储。新模型入口只注册原子工具/计划提议，旧更新入口暂供现有前端兼容，最终迁移后下线；不同时暴露两套相同语义工具供模型选择。

实现影响：`tools.py`、新编排模块与存储迁移、`chat_store.py`、`model.py`、`api.py`、前端回执与卡片适配。先加行为测试，再改变运行时，保留原测试站直到验证通过。

确定性验收：缺少素材也保存要求；复合请求按依赖执行；非法组合整计划拒绝；中途失败保留前步；重试与崩溃恢复不重复写；外部版本冲突停止；旧卡不可推进；用户事件恢复同一任务；暂停/取消保留明确边界；无隐式付费。

模型验收须同时核对意图、计划结构和真实持久化结果。分别测试明确启动、歧义澄清、要求先于选图、来源切换、已有素材、改口、多任务焦点与失败恢复。原来源卡脚本只有 20 个组合，不覆盖完整编排验收；修正合理澄清和部分要求的判定后再建立固定语料对照，不将两轮原始通过率作为架构成效证据。

第一片完成标准：单任务图片编辑的原子工具、持久化有界编排和用户等待恢复全部通过，再部署自然语音测试。多任务并行、通用 DAG 调度和能力缺口自动开发不在本片范围。


## 已确认的职责与工具链收口

模型负责上下文理解、任务拆解、工具选择、参数组织、追问以及依据回执继续调度；程序负责真实状态、生命周期、依赖校验、执行、版本检查、幂等和恢复。模型不只是意图分类器，程序也不通过新增口语关键词代替语义编排。

目标循环为：用户文字/语音或界面事件 → 服务端提供真实状态与工具目录 → 模型提出下一步调用 → 程序校验执行 → 回执回到模型 → 继续调度、等待用户或表达结果。循环有调用次数与时间预算；等待用户即停止调用，收到新事件后续接。失败预算耗尽保留任务并解释失败，不后台无限重试。

第一片仍限制每次最多四步、串行执行；不要求模型预先生成整条工作流。确认后续模型调用不得重复执行已成功步骤。OpenTalking 使用同一轮已确认的回复与操作结果进行表达，不建立另一份独立业务决策上下文。

### 现有代码事实与缺口

以下基于 `src/apps/companion_runtime/tools.py` 注册项，只表示代码存在，不证明自然语音端到端验收通过。

| 能力 | 已注册接口 | 收口事项 |
|---|---|---|
| 图片/视频任务草稿 | media.draft.start/update | 拆分导航与要求写入；接入有界执行及等待恢复 |
| 照片统计、检索与读取 | photo.album.count/list、photo.item.read | 保持浏览/整理分离，分页与当前选中照片进入统一上下文 |
| 相册整理与照片操作 | photo.organize.start/input、photo.action | 分析/资料编辑/删除为确认提议，不能当作完成回执 |
| 日记 | diary.open/list/read/save_draft | 保存依赖当前会话真实草稿；编辑与持续记录需核对现有前端/API能力，不能假定全已注册 |
| 个人记忆 | memory.save/search/list/delete | 写入/删除走确认；知识库检索不能等同个人记忆搜索 |
| 上传 | 当前模型来源动作仅打开上传卡片 | 真实文件选择、上传成功及素材绑定必须由客户端事件返回；模型不能声称已上传 |

统一工具契约至少包含：名称、用途、输入/结果 schema、前置条件、效果类型、确认条件、错误码、可重试性。任务状态和权限来自服务端；工具目录只暴露实际可执行能力。卡片属于工具结果，使用注册卡片类型，不接受模型任意生成可执行界面。

无法完成请求时记录能力缺口（用户原话引用、当前任务/焦点、缺失能力、失败阶段），作为开发待办；不得自动扩权、生成并执行新工具。缺口记录需去重，不能保存密钥或不必要的私密内容。

### 下一片验证边界

先完善固定单轮与多轮评测：启动修改→来源选择→真实素材事件→要求修改→暂停写日记→恢复原任务，同时覆盖失败与重复请求。严格比较完整参数，启动语句/来源指令混入brief判失败。

用同一工具契约、状态快照及场景对比云端参考和本机候选。当前0.5B实验未通过，不接管在线调度。评测阶段默认使用合成状态与假执行器，不能调用生产删除、保存或付费生成。程序状态正确与模型编排正确分别计分，再统计整个任务完成率。
