## 问题证据

真实模型曾在 `open_album` 动作中携带修改要求。当前执行器只执行导航，不保存同次调用的 brief。单个更新工具同时暴露导航、选图和要求修改，结构校验没有识别这种动作与字段冲突。这是已观察到的契约问题；等待选图的上下文是否促使模型重复导航，仍需对照验证。

只拆工具名称不能解决一个请求涉及多个步骤的问题，因此同时引入服务端任务编排。模型负责理解并提出计划，执行器负责依赖、版本、权限、暂停点与实际回执。

## 原子工具

以下是拟定接口，参数最终由严格 schema 定义，不接受无关字段。

| 工具 | 输入 | 效果 |
|---|---|---|
| `media.task.ensure` | 类型、可选当前任务引用 | 创建任务或取得当前同类任务，不覆盖已有要求 |
| `media.brief.set` | 任务引用、完整修改要求 | 独立保存要求；不依赖选图完成，不打开界面 |
| `media.source.request` | 任务引用、来源 upload/album/ask | 生成来源或选图卡片；不绑定素材、不写要求 |
| `media.asset.bind` | 任务引用、槽位、已验证素材引用 | 绑定上传或相册选择产生的真实素材 |
| `media.task.pause` | 任务引用 | 暂停并保留草稿 |
| `media.task.cancel` | 任务引用 | 明确取消任务 |

参数设置、生成预览与付费提交继续复用既有能力；后续逐项原子化。本片不改变图片/视频模式支持范围。按钮专用事件不暴露给模型。

`brief.set` 是替换完整要求，模型须保留此前未被撤销的约束；歧义时询问，不能猜测。运行时对不匹配动作的参数直接拒绝，不能默默忽略。

## 任务与计划分层

任务保存长期业务状态：类型、要求、素材、设置和版本。计划记录一次用户请求如何推进任务，不复制一份业务状态。

计划包含 `plan_id`、源消息 ID、任务绑定、步骤、依赖、状态和回执。步骤只引用注册工具，任务引用由服务端绑定当前真实任务；用户明确切换任务需单独处理，不能让模型任填其他任务 ID。

步骤状态：`pending`、`running`、`waiting_user`、`succeeded`、`failed`、`cancelled`。计划可处于执行、等待、失败、完成或取消状态。界面焦点是输入，不是执行成功证明。

示例：“修改一张照片，把背景换成海边，人物不变，从相册选。”

```json
{
  "steps": [
    {"id":"task","tool":"media.task.ensure","arguments":{"type":"image_edit"},"depends_on":[]},
    {"id":"brief","tool":"media.brief.set","task_from":"task","arguments":{"brief":"背景换成海边，人物保持不变"},"depends_on":["task"]},
    {"id":"source","tool":"media.source.request","task_from":"task","arguments":{"source":"album"},"depends_on":["brief"]}
  ]
}
```

该示例为提议格式，不是已上线 API。服务端验证无环依赖、工具允许列表及参数；限制为最多 4 步、串行执行、每轮至多一个等待用户步骤且必须在末尾。禁止任意对象路径插值；`task_from` 只能引用前置 ensure 的任务结果。

来源步骤发出卡片后进入 `waiting_user`；浏览器展示只更新界面回执，真实上传或选图完成才产生素材事件。素材事件执行 `asset.bind` 后结束该等待，不自动提交生成。用户只说了修改要求时，先存要求，再由任务缺项决定询问素材；不能因素材缺失丢弃要求。

## 编排执行规则

1. 校验整个提议的结构、依赖和工具可用性，再开始执行。每步运行前仍检查业务前置条件。
2. 同一任务串行写入。模型给出计划时绑定初始版本；计划内后续步骤使用上一成功步骤的真实版本。外部并发修改引发冲突时停止，不静默重基或重新解释用户原话。
3. 每步使用稳定的 `plan_id + step_id` 幂等键。网络重试读取已完成回执，不再次创建任务、上传或提交生成。
4. 每步事务提交业务变化和执行回执。前步成功、后步失败时保留已保存要求；计划明确标注部分完成，不把整个请求报成功，也不回滚用户已确认事实。
5. 崩溃恢复从持久化回执继续；不能确认外部副作用的步骤先对账，不能盲重试。第一片仅允许本地草稿变更与卡片请求，不编排外部付费副作用。
6. 等待用户期间释放执行锁。用户改口触发计划修订或暂停，旧卡不能推进新版本。等待状态不得后台重复调用模型。
7. 删除、覆盖、外部分析及付费操作保持各自既有确认规则；计划批准不等于用户批准所有副作用。

## 模型与表达

首片一次模型调用提出有界计划，不引入无限工具循环或第二个自主业务 Agent。计划执行器无语义判断，不通过关键词猜意图。

工具目录包含前置条件、输入和结果 schema；模型上下文包含当前任务、允许能力、用户原话及最近回执。具体任务 ID/版本仍由服务端限定。

编排回执生成一份消息和下一步卡片。例如：“修改要求记下了，请选一张照片。”OpenTalking 播放同一份文本；模型不得另说已完成修图。失败时明确哪个步骤完成、哪个未完成，不向用户展示工具协议文本。

## 已确认的职责与工具链收口

模型负责上下文理解、任务拆解、工具选择、参数组织、追问以及依据回执继续调度；程序负责真实状态、生命周期、依赖校验、执行、版本检查、幂等和恢复。模型不只是意图分类器，程序也不通过新增口语关键词代替语义编排。

目标循环为：用户文字/语音或界面事件 → 服务端提供真实状态与工具目录 → 模型提出下一步调用 → 程序校验执行 → 回执回到模型 → 继续调度、等待用户或表达结果。循环有调用次数与时间预算；等待用户即停止调用，收到新事件后续接。失败预算耗尽保留任务并解释失败，不后台无限重试。

第一片仍限制每次最多四步、串行执行；不要求模型预先生成整条工作流。确认后续模型调用不得重复执行已成功步骤。OpenTalking 使用同一轮已确认的回复与操作结果进行表达，不建立另一份独立业务决策上下文。

无法完成请求时记录能力缺口（用户原话引用、当前任务/焦点、缺失能力、失败阶段），作为开发待办；不得自动扩权、生成并执行新工具。缺口记录需去重，不能保存密钥或不必要的私密内容。

## 统一工具运行协议：执行、等待、查询与状态同步

本节为目标契约，尚未实现。注册不能止于函数名与参数schema，必须同时声明生命周期和同步/异步行为。

### 注册描述

每个工具声明 input_schema、result_schema、execution_mode（sync/async）、effect（read/draft/write/external）、preconditions、confirmation_policy、timeout_policy、retry_policy、cancellation_policy 和结果可见范围。sync/async表示执行方式，与是否需要用户确认无关。预检失败不能报告已接受执行。

### 调用与回执

调用携带 operation_id（幂等键）、session_id、task_id（若适用）、expected_revision（写操作必需）、工具名与arguments。用户身份由服务端认证绑定，模型不能自选owner。首次创建任务可没有task_id，以回执绑定真实ID。

统一回执包含 operation_id、task_id、status、revision、event_seq、result、error、wait、next_actions。未适用字段为空；result必须满足对应工具的结果schema。error包含稳定code、可重试标志和安全说明，不能仅返回自由文本。

状态为 accepted、running、waiting_user、waiting_external、succeeded、failed、cancelled。同步工具可直接返回终态；异步工具返回accepted及operation_id，最终结果必须另行回传。HTTP成功只表示请求协议成功，accepted不表示业务完成。

等待用户必须提供wait_id、原因、注册卡片类型、所需字段和允许事件；如选图、确认或补充参数。提交响应时绑定wait_id与版本；原子消费等待，重复点击返回原回执，过期卡片拒绝推进。等待外部系统需记录可查询的job引用与截止策略；超时但无法确认外部副作用时，保持waiting_external并标注需对账，不谎报失败或盲重试。

### 生命周期管理接口

运行时统一提供 execute、get_operation、list_task_operations、get_task、submit_wait_response、cancel_operation 和事件订阅。名称是协议职责，不代表现有路由。查询无副作用；取消可能只接受请求，只有工作器或外部系统确认取消后才进入cancelled；已完成操作不能伪装被取消。重试复用原幂等键查询或继续原操作；修改参数是新操作并重新校验版本。生命周期接口按角色授权，模型不一定能调用所有管理接口。

### 状态同步与模型调度

服务端是状态事实源。客户端与模型读取同一task快照及操作回执，不各自维护完成状态。事件至少含event_id、task_id、operation_id、revision、event_seq、类型和安全payload。事件可重复投递，接收方按ID去重、按序号识别缺口；重连先补快照和缺失事件，不靠浏览器是否显示卡片判断执行完成。

事件与业务写入需保证事务一致性（如持久化outbox），再异步投递。客户端事件输入也经过业务接口校验。图片上传成功、素材绑定完成、资料保存成功、后台分析完成均为独立真实事件。

模型只在新用户输入、有效等待响应或相关操作结果到达时恢复调度；不持续轮询模型。进度事件用于刷新界面，不必每个事件调用模型。多个结果合并形成最新快照，每个可调度事件记录处理凭据，避免重复推理产生重复副作用。前端可用SSE接收更新，断线时用查询补齐；传输方式不改变状态语义。

### 第一片验收

1. 同步查询直接终态；异步分析先accepted、后真实结果，期间不说已完成。
2. 选图进入waiting_user，用户响应后恢复原任务及要求；重复响应不重复绑定。
3. 请求超时后查询原operation得到真实结果，不重复写入或计费。
4. 断线重连、重复/乱序事件最终与服务端快照一致。
5. 取消竞态、外部结果延迟及版本冲突均有明确回执，不误报完成。
6. 模型、界面、语音依据同一任务回执表述状态；工作中、等待中与完成可区分。

该协议先通过假执行器和合成任务验证，再逐项适配现有相册、日记和创作工具，不将现有注册项存在视为协议已贯通。

## 实现进度：隔离持久化操作仓库

2026-10-29：新增 `operation_store.py`，使用单独显式初始化的SQLite数据库，尚未接入现有Companion数据库或在线API。

代码事实：按owner/session隔离任务及操作；保存原始调用、当前回执、命令幂等记录与持久化事件。相同操作键且输入一致返回现有回执；输入变化拒绝。命令重试返回该命令原回执，不回退操作当前状态。事务内检查操作序号及真实任务版本；业务变更、版本递增、回执和事件在同一SQLite事务提交。等待响应必须匹配wait_id和允许事件，并通过事务串行消费。提供读取操作、任务、有限操作列表和按持久化游标分页读取事件。

可信本地适配器可通过事务回调修改同库业务数据，必须声明用于幂等比较的business_input。回调禁止自行提交、调用网络或执行其他外部副作用；仓库不提供外部系统exactly-once保证。生产业务目前仍在原存储，不能跨两个数据库假定原子性，正式适配前须共用数据库事务。

范围限制：这验证的是本地事务与隔离操作仓库，不是进程强杀或断电测试，不证明外部任务恢复、在线鉴权、全局任务生命周期或模型理解能力。操作事件是可查询的持久化日志，尚无投递工作器、订阅确认、SSE或模型调度恢复。当前operation_id幂等范围为owner/session；调用方必须保持原会话。冲突操作当前保持原回执并抛出Conflict，需后续调度器显式重新核对状态。
