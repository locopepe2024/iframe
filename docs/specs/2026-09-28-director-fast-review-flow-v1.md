# Director 快速审阅与拍摄闭环 v1

## 目标

Director 的主要产物是可执行的拍摄决定。用户应能在原文、导演理解和拍摄计划之间快速往返，并通过 diff 判断每次修改的影响。事实证据账本是内部约束层，不应成为导演反复点击的工作流门槛。

## 用户流程

```text
剧本原文
  ↓ 分析
Director 理解（草稿）
  ↓ 查看 Director diff
  ↓ 一次采用
拍摄计划（草稿）
  ↓ 修改 / 重新生成
拍摄计划确认
```

导演修改 Director 理解后，系统保存一份相对上一版的 Director diff，并将拍摄计划标记为需要复核。用户可以查看 diff、采用当前理解并重新生成计划；不要求再次逐条确认事实账本或故事地图。

## Director 理解的组成

一次 Director revision 包含以下内容，并作为一个整体编辑和采用：

1. 故事确认与导演总览。
2. 剧情时间线、人物关系和剧情线。
3. 连续性约束：后续拍摄必须保持的状态。
4. 严格一致性：禁止新增、改写或无依据推断的边界。
5. 待确认问题：需要导演决定、但剧本没有明确给出的事项。

“提出修改”作用于以上全部内容。用户可以提出一个综合修改要求，模型返回新的 Director 草稿和可读 diff；也可以直接编辑其中任一部分，最终仍作为同一个 Director revision 采用。

## 状态边界

- `ScriptFactLedger`：原文证据索引，供系统校验和引用；默认不作为导演页面的主要操作入口。它不是 Director 理解，也不是用户需要反复确认的拍摄步骤。
- `DirectorProfile draft`：导演当前理解和修改内容。
- `DirectorProfile confirmed revision`：用户一次确认后供拍摄计划使用。
- `Director diff`：上一版确认理解与当前草稿的可读差异，至少覆盖新增、删除、修改的阶段、事件、人物关系和导演意图。
- `ShootingPlan draft`：基于当前确认 Director 理解生成；Director revision 变化后自动标记 stale。
- `Script revision diff`：剧本原文版本之间的差异，例如新增、删除或改写的对白、场景和事实。它与 Director diff 分开显示，不把原文变化误认为导演决定。

## 交互要求

1. Director 页面自动保存草稿；用户不需要把“保存草稿”当作工作流确认步骤。
2. 页面唯一的明确采用动作是“采用当前 Director 理解”。它同时采用总览、时间线、关系、剧情线、连续性约束、严格一致性和待确认问题。
3. 事实证据在需要时作为引用详情展开，不要求用户先确认独立事实账本才能继续拍摄设计。
4. 故事地图是 Director 理解的可视化编辑区；采用 Director 理解时一并生效，不再要求单独确认故事地图。
5. 拍摄计划错误必须给出直接动作：`采用当前 Director 理解` 或 `重新生成拍摄计划`。
6. 重新分析只产生新的 Director 草稿和 Director diff，不修改剧本原文，不自动覆盖用户已经采用的拍摄决定。
7. 计划生成使用最近一次已采用的 Director revision；草稿修改不应被下游消费。
8. 高级 JSON 不要求用户编辑字段细节；提供 Director 理解的 Markdown 导入/导出，用于备份、迁移和外部审阅。

## 不在本切片内

- 不删除事实账本数据或历史版本。
- 不把 Director 解释写回剧本原文。
- 不自动确认存在冲突的事实；证据仍保留供审计和模型约束。

## 验收

- 用户只需一次“采用 Director 理解”，即可进入拍摄计划生成。
- 修改 Director 草稿后能查看与上一版的 diff。
- Director 采用后，旧拍摄计划显示 stale，并提供重新生成入口。
- 不再出现要求用户先单独确认 visual story map 或 fact ledger 才能继续的阻断提示。
- 剧本版本 diff 与 Director diff 分开展示，用户能明确知道是原文变了，还是导演理解变了。
- “保存草稿”不再作为独立确认语义；自动保存或显式保存只是防止输入丢失。
