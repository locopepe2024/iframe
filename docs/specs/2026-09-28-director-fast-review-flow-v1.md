# Director 快速审阅与拍摄闭环 v1

## 目标

Director 的主要产物是可执行的拍摄决定。用户应能在原文、导演理解和拍摄计划之间快速往返，并通过 diff 判断每次修改的影响。事实证据账本是内部约束层，不应成为导演反复点击的工作流门槛。

## 用户流程

```text
剧本原文（只读）
  ↓ 分析
1. 导演理解（确认原作）
  ↓ 接受导演修订项
导演修订版（叠加层，不改写原文）
  ↓
2. 导演意图（艺术加工）
  ↓ 查看 Director diff
  ↓ 一次采用
拍摄计划（草稿）
  ↓ 修改 / 重新生成
拍摄计划确认
```

导演修改 Director 理解后，系统保存一份相对上一版的 Director diff，并将拍摄计划标记为需要复核。用户可以查看 diff、采用当前理解并重新生成计划；不要求再次逐条确认事实账本或故事地图。

## Director 理解的组成

一次 Director revision 包含以下内容，并作为一个整体编辑和采用，但这些内容不应全部作为顶层用户导航：

1. 故事确认与导演总览。
2. 剧情时间线、人物关系和剧情线。
3. 连续性约束：后续拍摄必须保持的状态。
4. 严格一致性：禁止新增、改写或无依据推断的边界。
5. 待确认问题：需要导演决定、但剧本没有明确给出的事项。

“提出修改”作用于以上全部内容。用户可以提出一个综合修改要求，模型返回新的 Director 草稿和可读 diff；也可以直接编辑其中任一部分，最终仍作为同一个 Director revision 采用。

导演可以提出补充、删除、澄清或保留建议，但这些建议先进入“导演修订版”，不会直接改写剧本原文。已接受的修订项作为下一次 Director 理解和导演意图的输入。

## 状态边界

- `ScriptFactLedger`：原文证据索引，供系统校验和引用；默认不作为导演页面的主要操作入口。它不是 Director 理解，也不是用户需要反复确认的拍摄步骤。
- `DirectorProfile draft`：导演当前理解和修改内容。
- `DirectorProfile confirmed revision`：用户一次确认后供拍摄计划使用。
- `Director diff`：上一版确认理解与当前草稿的可读差异，至少覆盖新增、删除、修改的阶段、事件、人物关系和导演意图。
- `ShootingPlan draft`：基于当前确认 Director 理解生成；Director revision 变化后自动标记 stale。
- `Script revision diff`：剧本原文版本之间的差异，例如新增、删除或改写的对白、场景和事实。它与 Director diff 分开显示，不把原文变化误认为导演决定。
- `Director revision proposal`：原文之上的结构化修订提案；不改变 `source_revision`，只作为后续 Director 理解和导演意图的输入。

## 两类 diff 的处理规则

### Script revision diff

剧本从 `source_revision N` 变为 `source_revision N+1` 后，系统先生成原文 diff，再判断影响范围，不默认重跑整本 Director 分析：

| 变化 | Director 处理 |
|---|---|
| 错别字、格式、标点 | 不重新分析；保留原 Director revision |
| 单句对白或局部措辞 | 检查对应事件、人物和剧情线，必要时生成局部 Director patch |
| 单个场景新增、删除或移动 | 局部重分析，并执行时间线、关系和连续性一致性检查 |
| 人物关系、结局或核心时间线变化 | 触发全局 Director 重分析 |
| 大段剧本重写 | 触发全局 Director 重分析 |

局部 patch 完成后必须运行全局一致性检查；如果检查发现其他阶段、关系或结局受到影响，则升级为全局重分析。剧本 diff 只描述原文变化，不直接修改 Director 已采用版本。

### Director diff

Director 草稿可由“提出修改”、回答导演问题或手动编辑产生。它比较两个 Director revision，覆盖时间线、人物关系、剧情线、连续性约束、严格一致性、待确认问题和视觉/表演意图；如果存在导演修订版，还要显示本次理解使用了哪些已接受修订项。

Director 草稿修改后的生效规则：

1. 自动保存草稿并生成 Director diff。
2. 未采用前，当前拍摄计划和已生成镜头继续使用旧 Director revision。
3. 用户点击“采用当前 Director 理解”后，生成新的 Director revision。
4. 采用后，旧拍摄计划标记为 `stale`，下一次拍摄计划生成使用新 revision。
5. 已生成镜头不自动删除；保留其原始 Director revision，并标记受影响状态，允许用户按需重新生成。

因此，导演可以快速修改理解而不破坏当前工作；只有采用修改后，变化才进入下一步拍摄计划。

## 交互要求

1. Director 页面自动保存草稿；用户不需要把“保存草稿”当作工作流确认步骤。
2. 页面唯一的明确采用动作是“采用当前 Director 理解”。它同时采用总览、时间线、关系、剧情线、连续性约束、严格一致性和待确认问题。
3. 事实证据在需要时作为引用详情展开，不要求用户先确认独立事实账本才能继续拍摄设计。
4. 故事地图是 Director 理解的可视化编辑区；采用 Director 理解时一并生效，不再要求单独确认故事地图。
5. 拍摄计划错误必须给出直接动作：`采用当前 Director 理解` 或 `重新生成拍摄计划`。
6. 重新分析只产生新的 Director 草稿和 Director diff，不修改剧本原文，不自动覆盖用户已经采用的拍摄决定。
7. 计划生成使用最近一次已采用的 Director revision；草稿修改不应被下游消费。
8. 高级 JSON 不要求用户编辑字段细节；提供 Director 理解的 Markdown 导入/导出，用于备份、迁移和外部审阅。
9. 剧本 diff 页面必须显示影响范围和建议动作：`无需重分析`、`局部修订` 或 `全局重分析`。
10. Director diff 页面必须显示受影响的拍摄计划、场景和镜头；未采用的 diff 不得改变下游产物。

## 阶梯式用户工作流

Director 不是把理解和艺术加工平铺在同一层，而是按以下顺序推进：

```text
剧本原文
  ↓
1. 导演理解（确认原作）
  ↓
2. 导演意图（艺术加工）
  ↓
拍摄计划与镜头设计
```

### 1. 导演理解：确认剧本原作

回答：

> 剧本实际写了什么？故事、人物、时间线和关系如何成立？

展示内容包括：

- 故事总览和核心冲突；
- 剧情时间线与事件；
- 人物关系与剧情线；
- 剧本版本 diff；
- 原文依据：对应的剧本片段、来源位置和依据状态；
- 导演问题：剧本没有明确说明、需要导演决定的事项。

这一层的目标是确认**对原作的理解是否正确**，不能把艺术加工写成剧本事实。

导演问题属于这一层，因为它们表示“原作哪里还不明确”。每个问题支持：

- 回答：将答案写入 Director 草稿；
- 增加：新增一个导演需要决定的问题；
- 暂不决定：保留为待确认项，不阻断其他工作。

回答问题不会修改剧本原文，只会更新导演理解草稿，并成为下一层导演意图的输入。

### 导演修订版：原文之上的叠加层

导演修订版不是新的剧本版本，也不是对原文文件的覆盖。每个修订项至少包含：

```text
revision_item
├── item_id
├── target：场景 / 事件 / 人物 / 对白 / 时间线
├── source_ref：原文位置
├── operation：补充 / 删除 / 澄清 / 保留
├── original_text：原文摘录
├── proposed_text：建议内容（可为空）
├── reason：导演修订理由
└── status：待处理 / 已接受 / 已拒绝
```

只有“已接受”的修订项才进入后续 Director 理解和导演意图；原文始终只读，并保留“原文 → 导演修订版”的差异。

### 增量重新理解

新增或接受修订项时，系统优先按 `source_ref` 只重算受影响的事件、人物、时间线和关系，再执行跨层一致性检查。若影响扩散到结局、核心关系或全局时间线，才升级为全部重新提交。导演修订版因此减少重复的全文理解，但不会隐藏地修改剧本。

### 2. 导演意图：艺术加工

回答：

> 在不改变原作的前提下，导演准备如何表达和加工？

展示内容包括：

- 视觉处理；
- 摄影和镜头倾向；
- 表演处理；
- 声音与节奏；
- 场景重点和需要强化的效果；
- 连续性约束；
- 严格一致性：禁止新增、改写或无依据推断的边界。

这一层的目标是形成**可执行的导演艺术加工**。它可以改变表达方式，但不能改写剧本原作。

### 3. 修订

用户可以从两个入口发起修订：

- **修订导演理解**：回答问题、修正时间线/关系/剧情线或补充原文依据；
- **修订导演意图**：修改视觉、表演、声音、节奏、连续性和严格一致性。

提交修订时必须选择范围：

- **局部修订**：只重新分析受影响的理解或意图，并做一次跨层一致性检查；
- **全部重新提交**：以当前剧本和当前导演要求重新生成完整的导演理解与导演意图草稿。

两种修订都会生成 Director diff，用户检查后再采用当前 Director 理解。修订范围选择不是剧本修改，不会改写原文。

### 可见但不独立成流程的内容

以下内容必须让用户看见、审阅并能进入修改，但不需要各自成为独立的确认流程：

- **剧本版本 diff**：显示原文 v1 → v2 的变化，并标注对 Director 理解的影响范围；
- **原文依据**：归属导演理解，显示每条理解对应的剧本原文、依据状态和来源位置；
- **连续性约束**：归属导演意图，显示后续拍摄必须保持的人物、时间、空间和道具状态；
- **严格一致性**：归属导演意图，显示禁止新增、改写或无依据推断的边界；
- **高级 JSON**：显示为可选的 Markdown 导入/导出，不作为默认编辑器。

这些内容分别归属于三个工作面：

| 内容 | 默认归属 | 用户动作 |
|---|---|---|
| 剧本版本 diff | 修订导演理解 | 查看影响、选择局部修订或全部重新提交 |
| 原文依据 | 导演理解 | 查看剧本片段、定位来源、识别不确定项 |
| 连续性约束 | 导演意图 | 修改需要保持的连续状态 |
| 严格一致性 | 导演意图 | 修改禁止新增或改写的边界 |
| Markdown 导入/导出 | 修订导演理解 | 备份、迁移和外部审阅 |

“可见”不等于“每项都要点击确认”：用户最终只需要在修订完成后采用当前 Director 理解。

## 用户术语与内部术语

用户界面统一使用 **“导演对剧本的理解”** 作为主概念，也可以在短标题中使用 **“剧本理解”**。每条理解下方显示“原文依据”，用于展示对应剧本片段和来源位置。

不要把用户工作面命名为“事实与证据”或“事实账本”。`ScriptFactLedger` 仅是内部持久化和校验结构，负责保存原文依据、来源范围和状态；它不是用户需要单独管理的内容，也不代表导演解释本身。

推荐显示结构：

```text
导演对剧本的理解
  ├── 故事总览 / 时间线 / 人物关系 / 剧情线
  ├── 导演问题
  └── 原文依据（展开查看对应剧本片段）

导演意图
  ├── 视觉 / 摄影 / 表演 / 声音 / 节奏
  ├── 连续性约束
  └── 严格一致性
```

## 功能域工作台 UI（实现约束）

Director 不再使用一张把所有字段连续堆叠的长页面。用户先看到三个工作面及其状态，再进入当前工作面处理问题。

### 顶部全局概览

页面顶部固定显示：

- 当前剧本版本和 Director revision；
- 当前草稿状态：`未修改`、`有未保存修改`、`有待采用 diff`、`需要复核`；
- 功能域完成度；
- 当前拍摄计划是否受影响；
- 唯一主操作：`采用当前 Director 理解`；
- 次要操作：`提出修改`、`导出 Markdown`、`导入 Markdown`。

顶部不展示长文本编辑器，只展示状态和下一步动作。

### 功能域卡片

功能域按导演工作顺序排列，每个域是一张可展开/收起的卡片或独立工作面：

| 工作面 | 作用 | 主要操作 |
|---|---|---|
| 导演理解 | 查看当前导演判断 | 阅读、局部编辑、查看图谱和 Director diff |
| 导演问题 | 处理模型发现的未知项 | 回答问题、增加问题、暂不决定 |
| 修订导演理解 | 让修改进入下一版草稿 | 选择局部修订或全部重新提交 |

每张卡片必须显示：

- 功能域名称和一句话作用；
- 当前状态：`未开始`、`草稿中`、`已检查`、`受上游变化影响`；
- 未处理项数量；
- 最近一次修改时间；
- 是否会影响拍摄计划；
- `展开编辑` 或 `查看 diff` 入口。

### 展开与提交规则

- 默认只展开用户当前选择的功能域，其他域收起但保留状态摘要。
- 功能域内部可以独立保存草稿，防止长时间输入丢失。
- 功能域保存只更新 Director draft，不单独生成 Director revision。
- “提出修改”可以从任一功能域发起，但模型返回的结果必须标注影响了哪些功能域。
- 如果修改跨域，顶部显示跨域影响提示，例如“时间线变化同时影响连续性约束和剧情线”。
- 用户可以从任一功能域跳到受影响的其他域，不需要返回页面顶部寻找字段。
- 最终统一使用“采用当前 Director 理解”，一次性采用所有功能域的当前草稿。

### 不使用的交互

- 不把所有内容展开成连续的上下滚动表单；
- 不让用户通过一个巨大 JSON 文本框编辑全部 Director 内容；
- 不在每个功能域放置独立的“确认生效”按钮；
- 不把事实证据字段和导演决策字段放在同一张编辑卡片里；
- 不让折叠状态隐藏未处理项或 stale 状态。

### 响应式布局

- 桌面端：左侧功能域导航/状态列表，右侧只显示当前域编辑器。
- 窄屏端：顶部横向功能域步骤条，下面显示当前域；支持展开/收起和返回功能域列表。
- 当前域切换应保留滚动位置和未保存草稿。
- 关键状态不能只用颜色表达，必须同时显示文字或图标标签。

## 不在本切片内

- 不删除事实账本数据或历史版本。
- 不把 Director 解释写回剧本原文。
- 不自动确认存在冲突的事实；证据仍保留供审计和模型约束。

## 验收

- 用户只需一次“采用 Director 理解”，即可进入拍摄计划生成。
- 修改 Director 草稿后能查看与上一版的 diff。
- Director 采用后，旧拍摄计划显示 stale，并提供重新生成入口。
- 不再出现要求用户先单独确认 visual story map 或 fact ledger 才能继续的阻断提示。
- 剧本版本 diff 与 Director diff 分开展示，用户能明确知道是原文变了，还是导演理解变了。
- “保存草稿”不再作为独立确认语义；自动保存或显式保存只是防止输入丢失。
- 剧本小改动不会默认触发整本 Director 重分析；结构性变化会升级为全局重分析。
- Director 直接修改在采用前不影响拍摄计划；采用后旧计划变为 stale，已生成镜头保留并显示其版本来源。
