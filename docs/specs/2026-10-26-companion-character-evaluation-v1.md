# 小安角色交互测试体系 v1

日期：2026-10-26。状态：测试规范与种子用例；未完成在线模型、浏览器或真人评测。

## 1. Observed：证据与现状

- **代码事实**：`src/apps/companion_runtime/personality.py` 有温和好奇、温和倾听、沉稳照料三种固定行为配置，约束追问、操作确认和事实表达。配置存在不等于长期角色一致性已经达标。
- **用户运行反馈**：曾出现日记编辑误转上传、停止后未继续采集、文字返回而没有语音等问题。这些反馈是回归用例来源；本轮未重新复现，不将其全部认定为当前版本仍存在的缺陷。
- **已有测试**：`tests/test_companion_{personality,intent,chat,diary,realtime}.py` 等覆盖部分组件行为；文件存在不代表真实手机、WebRTC 和跨会话链路已通过。
- **论文资料**：InCharacter 区分角色知识/风格与性格保真；SOTOPIA 研究情境中的社会互动；ESConv 标注支持策略；Qwen2.5-Omni 描述 Thinker–Talker。它们提供测试维度，不能证明本项目的架构成熟或适合老人。

## 2. Direct implication：先固定测试接口，再比较架构

把“感受—思考—表达”当作待验证的功能划分，不预设三个独立模型或服务。先用现有 Qwen/OpenTalking 做基线，再测试增加情绪线索是否改善回应，最后测试动态表达控制是否改善听感。

需要同时观察六个维度，分别出结果，不汇总成掩盖缺陷的单一总分：

| 维度 | 核心问题 | 证据 |
|---|---|---|
| 识别与线索 | 说了什么？声音线索是否可靠？ | 原音频、ASR 原文、标签、unknown、来源；人工转写 |
| 语义与工作状态 | 此刻在聊天、续写日记还是创作？ | 完整上下文、显式编辑状态、路由与工具实际执行记录 |
| 事实与记忆 | 是否记错、猜测亲属、忽略用户纠正？ | 来源消息、确认/纠正事件、检索与写入结果 |
| 角色与回应策略 | 是否倾听、克制追问、尊重休息？ | 多轮行为、用户反馈、盲评；不只看模型自述性格 |
| 表达 | 语气、语速和停顿是否合适？ | 实际播放音频及数字人；不能由文本推断声音效果 |
| 会话与播放 | 是否听完、能打断、能恢复、销毁后停止？ | 浏览器播放/采集状态、服务端事件、音频和会话 ID |

## 3. 首批用例和输入结构

机器可读用例：`tests/fixtures/companion_character/cases.v1.jsonl`，共 24 条。使用合成场景，不复用老人私密照片或原音频。每条包括上下文、用户原话、固定初始状态、预期观察、禁止结果、人工评审要求。用例不规定唯一回复文案。

测试时钟固定在 2026-10-26、Asia/Hong_Kong，运行日志同时保存 UTC 时间与当地日期；不依赖机器当前时间。每条从隔离工作区与规定状态启动。跨会话测试显式串联会话，其他测试不得共享记忆。

种子集分组：

- 情绪与上下文配对 6 条：同文不同语气、同语气不同语境；声学标签与用户原话冲突、标签缺失。
- 角色与边界 4 条：少问、休息、能力说明、用户纠正。
- 日记与意图 5 条：持续记录、明确停止、确认保存、当天上下文、创作指令与描述分开。
- 记忆 3 条：未知不猜、确认后写入、跨会话纠正。
- 声音与生命周期 6 条：语音/文字设置、打断、播放后恢复收音、断线、退出清理。

音频用例目前只有采集计划，**没有对应录音**。文本回放不能代替这些用例的执行。后续录制相同句子的平静/开心/低落版本，配合不同语境；记录说话人自述意图和独立听评，不将表演标签视为真实心理状态。按说话人和场景划分开发集与保留集，不把同一说话人的近重复录音随机分到两边。

## 4. 测试层次与执行

### L0：离线约束回归

复用现有 personality、intent、diary、chat、realtime 测试；测试确定的状态转移、用户纠错优先、操作确认、过期轮次丢弃。不能用正则关键词替代语义正确性判断。

新增 `scripts/companion_eval/check_cases.py` 只校验种子集的完整性与覆盖分布，**不执行模型、不验证产品行为、不产出“角色能力通过率”**。

```bash
python3 scripts/companion_eval/check_cases.py
```

### L1：模型回放

未来适配器读取用例、重建上下文，调用真实运行链路，保存原始请求配置、回复、工具执行和状态。先做文本基线；用户授权渠道与计费范围后再跑远端请求。本轮没有新增远端模型调用。

每个用例运行 3 次仅用于发现不稳定；报告逐次通过数，不把 3 次当统计充分性。失败要定位识别、上下文、路由、工具、TTS 或浏览器边界，不能用模糊兜底隐藏。

### L2：浏览器端到端

在移动尺寸浏览器上验证上传/日记/播放/收音状态和实际持久化。对本地 Mock 注入断线、延迟、过期回包；用真实 WebRTC 验证媒体轨道。桌面模拟通过不能声称手机麦克风权限、回声消除和蓝牙已经通过。

语音文字模式是持久设置，进入新会话后也要验证。播音结束后是否重新收音，需同时核对 UI、采集轨道与实际收到的下一轮音频，不能仅看“我在听”。

### L3：表达盲评与目标用户观察

同一上下文比较 A/B，隐藏模型与配置、随机播放顺序；先分别评文本与音频，再评完整交互。至少两名评审独立给分并记录分歧；分歧未解决时保留分布。普通开发者评审不能替代目标老人可用性测试。

人工维度 1–5 分，锚点：1=明显不合适/妨碍表达；3=可接受但机械；5=自然、清楚且尊重用户。分别评情境适切、角色一致、声音自然、易理解与继续操作的容易程度。没有音频时，声音项必须标记未评。

不把“聊得越久”“越像真人”设为默认成功指标；观察老人能否理解状态、完成任务、纠错和主动结束。

## 5. 实验与验收门槛

以下是**建议的 Demo 门槛，尚未实测**：

1. 硬约束：未经确认的持久写入/删除、过期回复落入新轮次、退出后继续采集，任一发生即阻断该候选版本。必须用实际状态/数据库/事件验证，模型说“没保存”不算证据。
2. 功能回归：首批适用用例完整执行，无未解释的回归。未实现、无音频、渠道故障分别标为未实现/未执行/环境阻塞，不能计为通过或悄悄排除；报告分母。
3. 人工质量：先给基线打分、记录真实失败，再据此预先约定候选版本门槛；此时不编造“情绪准确率 90%”或“体验提升 30%”。
4. 性能：记录用户话音结束→转写完成→首字→首个可听声音，以及打断→停止播放的 p50/p95、失败数和有效样本数。首音由浏览器可听播放事件与录制核对，不能用服务端收到音频代替。先测基线再定预算。

消融顺序：A=现有文本理解+固定语气；B=A+可选声音线索；C=B+回应策略；D=C+动态表达（仅在渠道实证支持时）。同一模型/版本/提示词/上下文/音频尽量保持一致，每次只改变一个因素。LLM 随机性、网络和说话人差异均记录；小样本偏好只能说“在本组用例中”，不推及所有老人。

## 6. 运行记录约定（待实现）

至少保存：run/case/session/utterance ID、用例集版本、代码版本、模型/渠道标识、提示词哈希、固定时钟与时区、初始状态、输入/输出引用、实际工具执行与最终状态、阶段耗时、失败边界、评审版本和未执行原因。不得保存 API key；录音默认不留存，确需留存需单独授权。对照运行的录音使用已授权固定样本。

自动结论限于可观察约束；人工判断、LLM 辅助评分、客观执行结果分别存放。评审看不到的事实标记 unknown。期望中的“策略”是可观察行为要求，不声称读取了模型内心，也不要求记录隐藏推理。

## 7. Not yet proven / Hypotheses

- **未证实**：SenseVoice 标签在老人、口音和家中噪声下可靠；增加标签能改善回应；当前 UniArt TTS 别名支持逐轮动态语气；三层拆分会改善延迟或自然度。
- **假设 H1**：工作状态与确认协议能减少日记误路由。用有/无状态的同组多轮回放检验。
- **假设 H2**：情绪线索对文本存在歧义的场景更有帮助。用同文不同语气配对、unknown 和错误标签注入检验；同时检查误导成本。
- **假设 H3**：回应策略比单纯调整声音更能改善情境适切性。先分离文本/音频盲评再评整链路。
- **假设 H4**：固定角色规则与纠错记忆可维持一致。用跨日、跨会话、长对话和冲突事实测试；短句自述不能证实。

## 9. 研究依据

以下核对到论文摘要/项目 README 或局部源码；属于聚焦调研，不是穷尽文献或复现实验：

- [InCharacter](https://arxiv.org/abs/2310.17976)：角色性格保真评估；心理量表不等于本产品临床有效性。
- [SOTOPIA](https://arxiv.org/abs/2310.11667)：情境中的社会互动评测；不能直接替代老人可用性测试。
- [ESConv](https://aclanthology.org/2021.acl-long.269/)：支持策略标注；不将日常陪伴强制套成心理咨询。
- [Generative Agents](https://arxiv.org/abs/2304.03442)：记忆、反思和计划；[检索代码](https://github.com/joonspk-research/generative_agents/blob/main/reverie/backend_server/persona/cognitive_modules/retrieve.py)存在新近性、重要度和 embedding 相关度计算，不证明本项目记忆实现具有相同效果。
- [RoleLLM](https://arxiv.org/abs/2310.00746)、[Character-LLM](https://arxiv.org/abs/2310.10158)、[CoSER](https://arxiv.org/abs/2502.09082)：角色知识、经历和情境模拟。文学角色数据与老人陪伴存在任务差异。
- [Qwen2.5-Omni](https://arxiv.org/abs/2503.20215)：Thinker–Talker 由隐藏表示生成音频 token；这不是现有 ASR→文本 LLM→TTS 集成已具备的能力证明。
- [AIRI](https://github.com/moeru-ai/airi)、[Open-LLM-VTuber](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber)：语音与形象交互参考。README 功能声明、源码存在、实际移动端稳定是不同证据层次；本轮未部署或验证这些项目。

## 10. 文本回放切片（2026-10-26）

范围：新增独立命令 `scripts/companion_eval/replay.py`，通过本地 TestClient 调用真实 FastAPI chat 路由、模型请求组装及临时 SQLite 存储。运行产物放在调用者指定的独立目录，每次拒绝覆盖现有目录。只使用合成用例；不读取个人渠道数据库、生产照片或历史对话。

两种传输：

- `offline` 默认：注入明确标注 synthetic 的上游响应。只验证请求组装、路由和持久化边界；不代表 Qwen 的回复质量或角色能力。
- `live` 可选：使用明确指定的 HTTPS base URL 与 `COMPANION_EVAL_API_KEY`，走同一模型解析与 API 路径。产生计费请求；离线校验与本轮回归不调用此模式。每条用例必须重新建库，不触碰生产库。

每条记录包含用例、执行范围、模型/提示词哈希、实际模型输入、模型原始消息、API 返回、执行前后记忆和日记、检查依据、耗时与人工待评项。存储时钟使用用例固定日期；模型接口当前不提供时钟参数，不声称模型已获得该日期。仅记录后端请求总时长与模型调用时长，不伪造首字或首音。

本切片支持 P01、P03、D04、M01、M02 的后端文本部分。语音用例统一未执行；需要浏览器工作状态、确认 UI、纠错修订和情绪服务的用例标记 `unsupported_state`，不能以自建替代状态冒充已有能力。当前接口只接收用户原话，没有完整助手历史；记录这一限制。

自动检查局限于：没有未经确认的记忆/日记写入、上下文送达、指定 profile 送达、M02 原话与确认预览绑定、D04 是否进入无记忆工具的写作通道。人工质量始终 `pending`。自动通过不等于场景全部通过；离线出现路由失败也不能据此认定移动端 UI 同样失败。

成功标准：完整记录全部 24 条的执行或未执行原因；离线/在线来源可辨；可检出已知路由边界和持久化违例；无凭据落盘；回放同一用例仍保持独立数据库。此切片不修改生产路由、不扩大意图正则、不部署模型。

## 11. 日记工作域组件回放切片

代码核对补充：`AgentChat.send` 在提交时调用 `diaryDay` / `diaryPrompt`，将自然语言日记请求变为明确日期的写作请求。因此 D04 的后端直连结果仅描述绕过前端的入口差异。`DiaryCard` / `DiaryEditor` 已提供独立编辑与听写，不应在 Python 适配器中发明另一套编辑状态模拟产品。

本切片以真实 React 组件回放 D01–D03：D01 将计划性原话作为内容追加，保持编辑且不调用 chat；D02 注入识别到的“停止”，验证停听、不保存、保留草稿；D03 请求保存后保留待确认，点击保存才调用日记 API，并验证失败重试保留原文与操作 ID。用例数据从同一 JSONL 读取，时钟固定在当天中午，避免漂移。

边界：组件测试 mock 日记 API 和浏览器识别事件，不验证实际 ASR、麦克风或真实数据库；D02 仍缺少音频端到端证据。独立运行既有后端日记测试，验证真实 SQLite 保存、重试、版本冲突和重新读取；两层通过也不能宣称同一次浏览器请求已贯通后端。

新增 `scripts/companion_eval/diary.py`，将两层原始测试报告和执行范围写入新的运行目录，保留全部 24 条的执行状态。前端运行范围包括自然语言日记请求转换、编辑器和日历的既有回归。报告不计算完整场景通过率，不覆盖上一轮基线。成功标准：D01–D03 组件行为有可定位断言，D04 转换有既有用例证据，两层测试独立出结果；任何子进程失败或报告缺失都不能计为通过。测试失败先记录原因，不扩大生产路由规则。

本轮组件观察：D01 符合所测约束；D02 完整句“就先说到这里，停止”被追加为正文，精确“停止”才停听；D03“保存这篇日记”被追加为正文，没有产生新的保存确认。D02/D03 标记 `component_expectation_mismatch`，不能因描述现状的回归断言通过而改成场景通过。下一步需设计可测试的自然命令识别及编辑/确认状态协议，避免简单将任何包含“停止/保存”的叙述误作命令。

## 12. 日记听写命令修正切片

范围：独立、可测试的 `diaryVoiceCommand` 分类函数；`useDiaryDictation` 消费分类结果；`DiaryEditor` 管理保存确认。只在日记听写工作域内使用，不修改聊天路由、不请求新模型。

命令集合有界：接受“请/帮我”这类礼貌前缀、停止/暂停记录、保存这篇日记、停止并保存等完整命令，以及“就先说到这里，停止”这一完整结束表达。只做整句匹配，不因正文含“保存/停止”就触发操作。命令表外的歧义表达继续作为正文，不声称覆盖任意自然语言。

状态：听写→停止命令→暂停且保留草稿；听写→保存命令→停止采集、显示确认、无持久写入；按钮确认→保存；取消确认→保留编辑内容、麦克风保持关闭；恢复听写需明确操作。确认期间改文会撤销旧确认，需重新点击保存。按钮“保存日记”本身是明确提交，沿用现有行为。保存失败保留内容、确认与重试操作标识。

先将 D02/D03 测试改成期望行为并记录失败，再实现；加入否定、条件句、引用、叙述和包含命令词的计划等对照。已有语音保存测试改为先确认再保存。过期识别事件不得在停听/确认后追加内容或重复提交。成功标准：D01–D03 回放检查通过，旧日历/听写回归通过，类型检查通过；真实麦克风与 ASR 仍未评测，不自动部署。

实施证据：D02/D03 在修正前按新期望断言失败；修正后两条均通过组件回放。日记语音保存统一进入按钮确认，包括原来的精确命令“保存日记”，不再直接写入。取消确认、编辑撤销旧确认、迟到识别回包和保存失败重试均有组件断言。修正前基线保留，不改写为通过。后续若引入模型语义分类，需沿用这些对照集，并另建保留集验证，不直接宣称语义覆盖完整。
