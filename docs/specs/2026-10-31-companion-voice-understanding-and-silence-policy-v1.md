# 小安语音理解、情绪与安静策略 v1

## 目标

让小安在语音陪伴中做到：

1. 只在有明确回应价值时说话。
2. 用户继续表达时保持安静，不抢话、不重复追问。
3. 能区分聊天、情绪陪伴和任务执行。
4. 任务成功、失败、等待、需要补充时各提示一次，并提供下一步动作。
5. 保留完整文字记录，但语音输出默认短、慢、可打断。

## 当前观察

- 语音识别和 OpenTalking 已能形成基本链路。
- Qwen 云端回复仍可能较长，连续语音时会形成排队。
- 任务结果已经有服务端状态，但语音层会把相同状态再次说出来。
- 当前系统缺少统一的“是否应该说话”判定层。
- 情绪理解尚无统一的输入、输出和评估标准。

以上是代码和运行日志支持的事实；“用户会因此感到打扰”是产品假设，需要通过测试验证。

## 核心模型：回应门

每次识别到用户语音后，先经过一个轻量回应门，再决定是否调用云端模型和 TTS。

```text
语音分段
  -> 语义/情绪信号提取
  -> 当前任务状态合并
  -> 回应门
       ├─ silent：只记录，不回复
       ├─ acknowledge：短确认，不追问
       ├─ ask：只问一个必要问题
       ├─ act：调用一个任务工具
       └─ respond：生成短文本并语音播放
```

回应门由程序维护最终状态，模型提供意图和情绪判断建议。模型不能直接决定已经成功，也不能绕过任务状态。

## 什么时候回应

### 必须回应

- 用户明确呼叫“小安”“在吗”等唤醒词。
- 用户提出明确问题或请求操作。
- 任务需要一个关键参数才能继续。
- 工具已经返回最终成功或失败。
- 检测到高置信度的明显情绪风险，需要关怀或升级提示。

### 可以只确认

- 用户正在连续讲述事实，暂时没有问题。
- 用户说“嗯”“好”“知道了”等结束性短句。
- 用户刚完成一个选择，系统已记录但还没有下一步动作。

示例：`嗯，我听着。`

### 应保持安静

- 用户在连续说话或短暂停顿，且没有完成语义单元。
- 同一任务仍在处理中，没有新的状态变化。
- 同一成功、失败或等待状态已经提示过。
- 用户正在查看照片、编辑资料或阅读日记时，不主动插话；用户发出的操作和口述仍须按当前焦点处理。
- 仅收到无法确定含义的重复片段，且没有新信息。

安静不等于丢弃：文字记录和任务事件仍然保存。

## 语音长度策略

- 确认：不超过 12 个汉字。
- 情绪回应：1～2 句，通常不超过 35 个汉字。
- 必要追问：只问一个问题，不提供长解释。
- 任务结果：状态 + 下一步，通常不超过 30 个汉字。
- 连续讲述期间不主动总结，除非用户说“总结”“写日记”“停一下”。

TTS 文本和聊天文字分离：聊天记录可完整，语音只读短版。

## 情绪理解 v1

### 输入信号

- 语音文本的情绪词、否定词、重复和语速变化。
- ASR 置信度和重复片段，仅作为弱信号。
- 当前任务是否失败、等待或被打断。
- 最近一次用户明确表达的情绪，不从助手推测事实。

### 输出标签

```json
{
  "valence": "positive|neutral|negative|mixed|unknown",
  "arousal": "low|medium|high|unknown",
  "need": "listen|comfort|solve|celebrate|clarify|none",
  "confidence": 0.0,
  "evidence": ["用户原话中的短片段"]
}
```

情绪标签只用于选择语气、长度和是否追问，不写入长期记忆，除非用户明确要求记录。

### 交互原则

- 高情绪、低明确请求：先陪伴，不马上给方案。
- 高情绪、明确任务：先承认感受，再执行任务。
- 低置信度：不说“你很焦虑/你很难过”，改为“听起来这件事让你有些着急吗？”
- 同一情绪只主动回应一次，用户继续讲述时保持倾听。

## 任务状态播报

每个任务保存 `last_announced_revision` 和 `last_announced_status`。

| 状态 | 首次提示 | 重复事件 | 用户可见下一步 |
|---|---|---|---|
| waiting_input | “还差一个信息：…” | 不重复 | 对应输入卡片 |
| running | “我正在处理。” | 静默，除非超时 | 查看进度/停止 |
| succeeded | “已完成。” | 不重复 | 查看结果/继续 |
| failed | “这次没有完成。” | 不重复 | 重试/修改/取消 |
| cancelled | “已取消。” | 不重复 | 重新开始 |

相同任务、相同 revision 的状态不能再次触发语音。用户主动询问状态时可以再次简短告知。

## 防重复规则

- 为每个回复生成 `response_reason`：`wake|question|ack|emotion|task_transition|error|silence`。
- 同一 `task_id + revision + response_reason` 只允许一次语音。
- 上一条助手语音仍在播放时，新回复进入队列；若只是确认或旧状态，直接丢弃语音但保留文字。
- 用户说话时立即停止当前播报，并优先处理新语音。
- 失败重试不能自动重复计费请求；只有用户明确说“重试”或点击重试才执行。

## 推荐的责任边界

- 浏览器：分段、打断、静音检测、播放队列。
- iframe 程序：任务生命周期、状态去重、回应门、焦点和工具结果。
- 本地协调器：轻量意图/焦点/情绪建议，不保存事实，不执行工具。
- Qwen：理解上下文、提出工具调用或短回复，不决定事实状态。
- OpenTalking：只负责已批准的语音表达和 WebRTC 播放，不承担任务编排。

## 分阶段实施

### P0：先控制话多和重复

- 建立 `response_reason` 和任务播报去重表。
- 让 TTS 使用短版文本，聊天记录保留完整文本。
- 用户开始说话时停止当前播报。
- 对 `running` 状态默认只提示一次。

成功标准：同一任务状态不重复播报；连续讲述时 3 轮内不主动插话。

### P1：回应门和安静策略

- 在 iframe 增加程序化回应门。
- 区分 `silent/acknowledge/ask/act/respond`。
- 相册、日记、照片编辑焦点下，语音保留给上下文编排和编辑通道，不因短句或情绪规则被静默。
- 增加“我在听”的低频确认，不能每个分段都说。

成功标准：无明确请求的短句不会触发云端 Qwen 和 TTS；用户主动呼叫仍有回应。

### P2：情绪理解

- 先用 Qwen 返回结构化情绪标签，不改变任务状态。
- 建立 20～30 条人工标注语音文本小样本，覆盖平静、开心、着急、失落、困惑、连续讲述。
- 评估标签准确度、误判率和不必要回应率。

成功标准：情绪误判不直接改变工具动作；低置信度时使用询问式表达。

### P3：人物化表达

- 将“温和、沉稳、好奇、克制”转为可测试的表达参数：最大句数、追问频率、确认词、沉默阈值。
- OpenTalking 只接收最终短文本和表达参数。

成功标准：同一任务不同性格只改变表达，不改变事实和工具执行。

## 必须建立的测试

1. 连续讲述：用户连续说 3～5 段，小安只确认一次。
2. 重复语音：同一句识别结果重复到达，不重复调用 Qwen/TTS。
3. 任务成功：工具成功回执后只播报一次。
4. 任务失败：失败后只提示一次，用户说“重试”才再次执行。
5. 查看照片：打开全图或资料编辑时，命令仍能进入当前焦点的处理链，不被静默规则吞掉。
6. 情绪低置信度：不直接断言情绪。
7. 打断：用户说话立即停止当前语音，下一句不丢失。
8. 长历史：完整历史可查询，但模型提示上下文保持上限。

## 近期优先级

先做 P0，再做 P1；暂不先改数字人外观、实时 TTS 或更复杂的端侧模型。当前最直接的质量收益来自：少说、去重、状态只播报一次、用户说话时让路。


## 2026-10-31 回应门修正与验证边界

代码事实：

- “继续、可以、好、好的、行”不再作为全局静默词；这些可能是任务回答。
- 有活动或暂停创作任务、照片工作流、照片/日记焦点时，短句静默和情绪快捷回复均让路给上下文处理。
- 情绪快捷回复仅匹配独立的第一人称感受短句；否定、引用、第三人称、问题或附带任务的句子交给模型理解。
- 近期已经作过同类情绪确认时，本轮交给模型，不再直接静默用户再次倾诉。

验证：新增用例先复现 16 个失败；修正后 `pytest -q tests/test_companion_voice_attention.py tests/test_companion_chat.py` 共 67 项通过。测试使用模拟模型，证明路由和上下文交接，不证明真实语音体验或模型理解准确度。

尚未完成：文本来源和语音来源未区分；无任务焦点的极短语气词仍走同一静默规则。关键词情绪信号未经人工标注评估，不能视为声学情绪识别。真正的语音起声打断、短版语音输出、基于实际播放回执的播报去重仍待收口；加载历史记录不能证明用户已经听过。


## 播报回执修正

- 删除根据聊天历史和提交播放请求提前标记“已播报”的逻辑。
- OpenTalkingReply 仅在匹配本轮 command 的 speech.ended 到达、播放未取消且组件仍有效时通知完成；被取消、阻止、超时或失败不写完成记录。
- AgentChat 依据该完成通知维护当前会话的任务播报集合，上限 200 项。刷新页面不自动重播历史，也不假设历史已被听过。
- 回执是服务端流程完成证据，不证明终端物理可听。当前仍没有持久化音频回执，也未实现逐句起声打断。
- 前端播放与播报辅助测试 16 项通过，类型检查通过；新增完成回执用例先失败后通过，覆盖无关回执、正常结束及取消。
