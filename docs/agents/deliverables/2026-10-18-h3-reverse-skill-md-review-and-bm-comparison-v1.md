# H3 reverse skill 全量 Markdown 复核与 bm_1 对照结论

日期：2026-10-18。来源仓库：`gnipbao/minimax-h3-video-reverse-skill`，分支 `codex/initial-release`，commit `2fd1cc182606b81b69e0a9dca31c6cc7c2e973af`。本次读取该分支全部 Markdown 文件；仓库文档和示例是方法规范与教学材料，不等于 H3 生成效果证明。

## Observed：仓库方法的共同主张

1. **先观察，再写提示词。** `video-observation.md` 要求完整读取时间线，快动作、遮挡、疑似切镜处补看连续片段；联系表只是导航，原帧仍是证据。
2. **时间有多个边界。** 区分容器时长、视觉时长和最后一帧时间；可变帧率使用真实 PTS，不能由平均 fps 推算精确帧时刻。
3. **事实按状态链记录。** `evidence-contract.md` 要把每个动作拆成可观察阶段，明确接触、撤回、再次发力、遮挡、再出现和实际终态；不把未看见的中间过程补成连续事实。
4. **Shot、段落、Job 分开。** 真实切镜决定 Shot，叙事段落服务编排，Job 服从平台时长能力。连续镜头切成多个 Job 时，后一段必须从切分点实际状态开始，不得回到开场姿态。
5. **锚点应少而关键。** 视觉锚点用于当前复刻结果中会改变理解的视角、初态、覆盖/揭露、几何变化和截止状态；仓库没有要求把每帧都写进自然语言提示词。
6. **适配器格式不是效果保证。** `h3-adapter.md` 明确三字段、首尾帧和平台能力需要分别核实；格式检查不能证明模型理解了动作或保留了节奏。`docs/validation.md` 明确该仓库没有执行 H3 生成和成片相似度测试。
7. **改编要显式。** 目标时长不同、合并镜头、删除剧情或改变连续性都应记录为 adapted；不能把改编后的结果称为源片逐帧忠实复刻。

## Direct implication：对当前 bm_1 实验的修正

### 1. 我们之前混合了两个问题

- `[video editing]` 允许编辑式重生成和重新组织；它适合测试“编辑后是否保留主体、场景和动作方向”，不适合单独证明源片节奏被硬锁定。
- `[reference generation]` 把视频作为动作、镜头和节奏参考；它更适合当前问题，但仓库方法也没有把普通视频参考定义为逐帧时间控制。
- 因此 `editing` 版本出现动作相位重组，不能直接归因于 H3 无法理解节奏；这可能是任务语义预期的一部分。

### 2. 帧锚点不能替代状态链

我们在 bm_1 中把源帧号大量写入 prompt，结果确实改善了运动连续性，但后段仍被重组。这与仓库规则一致：帧号只是证据索引，真正可执行的内容应是“状态→变化→下一状态→持续/终止条件”。锚点过密还可能增加文字负担，却没有告诉模型接触、回落、重新发力等关系。

### 3. 2 秒切点应当作为 Job/Shot 状态边界测试

`[Shot 1]` / `[Shot 2]` 的写法只能表达连续时间线；它不能把普通参考视频变成硬切点控制。若要验证切点，必须记录：切点前最后状态、切点后第一状态、是否同一连续镜头、是否允许重编排。仓库示例强调后一 Job 的 opening state 不能退回开场；这比单独写 `At 00:02.000` 更重要。

## bm_1 实验的统一对照

| 版本 | 任务语义 | 人物 | 动作/节奏观察 | 主要指标 |
|---|---|---|---|---|
| baseline | reference generation | 单机器人稳定 | 前段接近，约 3.08 秒后冻结 | 90 帧，3.75 秒 |
| two-shot | video editing，2 秒切点 | 稳定 | 不冻结，但 2 秒后动作重组 | 运动密度前后接近 |
| frame-anchor | video editing，0.5 秒锚点 | 稳定 | 连续性改善，后段仍漂移 | 同序号 ±1：55/90 |
| dense | video editing，0.25 秒锚点 | 稳定 | 不冻结，2 秒后仍重组 | 同序号 ±1：30/90 |
| tempo | video editing，锚点+快慢语义 | 稳定 | 前后运动密度接近，源相位仍漂移 | 同序号 ±1：34/90 |
| reference-tempo | reference generation，锚点+快慢语义 | 稳定 | 比 editing 稍接近源时间，但仍重组 | 同序号 ±1：39/90；相同时间误差中位数 17.70 |

这些像素指标只作为辅助；当前主要验收仍是人物、动作顺序、相对节奏。所有版本的输出均为 24 fps、90 帧、3.75 秒；本轮不把 30→24 映射作为主因诊断。

## Not yet proven

- H3 是否能在 reference generation 下稳定保留每个动作阶段的相对持续时间：尚未证明。
- `reference-tempo` 比 editing 版本更好是否可复现：当前只有一次/版本，尚无统计支持。
- 帧锚点数量增加是否真正改善节奏，还是仅改变了动作候选：尚未隔离。
- 仓库示例中的方法能否直接提升 UniArt H3 成片质量：仓库自身明确没有 H3 生成相似度验证。

## Hypotheses

1. reference generation 比 video editing 更适合动作节奏迁移，但仍只提供软参考。
2. 节奏信息应以动作阶段和持续关系表达，而不是继续堆积帧号。
3. 最有价值的下一轮不是更密帧锚点，而是“状态链 + 少量锚点 + 区间速度 + 终态”四部分的最小提示词。
4. 如果该最小 reference generation 版本仍能保持人物和动作顺序，却持续重组后半段，说明普通视频参考的时间控制能力有限。

## What would verify it

下一轮只做一个 reference generation 版本，固定素材、seed、人物图和输出参数：

1. 用 6–8 个关键锚点替代每 0.25 秒帧号；每个锚点写可见状态，不写未观察的意图。
2. 每个相邻锚点之间写清变化方向、相对速度、是否短暂保持、是否必须连续。
3. 明确 2 秒切点前后的 opening/closing state，但不把切点描述成模型硬控制参数。
4. 按三项验收：人物稳定、动作阶段顺序、相对节奏密度；逐帧匹配只作为附加记录。
5. 与 `reference-tempo` 做一次受控对照。若最小状态链版本仍重组，则停止继续堆提示词，把结论降为“模型软参考不足”，再评估白模/姿态视频作为额外参考。

## 证据边界

仓库全量 Markdown 提供的是流程、契约、反测和格式边界；其 `validation.md` 明确没有执行 H3 生成或成片相似度测试。因此本报告把仓库规则作为算法/工作流启发，不把仓库自述升级为 H3 性能事实。bm_1 的运行判断来自本地保存的实际输出和逐帧辅助测量。
