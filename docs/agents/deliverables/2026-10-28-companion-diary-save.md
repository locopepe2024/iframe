# 聊天中的日记保存闭环

代码事实：此前注册能力只有日记打开、查询、阅读，没有保存工具；模型因此只能回复手动保存说明。运行观察：报告会话对应日期日记条数为0，最近保存请求先完成文本回复、后一次失败。服务日志记录 Invalid text reply，尚无当时原始返回形状，不能推断是额度、超时或渠道断开。

实现 9f3fa9b5：增加 diary.save_draft(source_turn_id)，只接受同用户、同actor、同会话中已完成且原请求明确按日期写日记的文本结果。正文与日期由服务端源记录读取，模型不能提交或改写。保存与回合完成共用事务；同草稿再次保存只报告已保存；当天已有其他版本或当前日记编辑焦点包含不同正文时，提示用户在编辑器核对，不覆盖。此工具不通过通用 tools POST 暴露写入，必须有已认领聊天回合。

交互约定：用户明确要求保存既有草稿时调用；只是提到日记、继续写或没有明确草稿时不调用。当前仍不支持通过该工具保存尚未同步到服务端的编辑器变更；需编辑器确认。

验证：先复现缺少保存工具的失败测试，再实现。33项相关测试通过，包括隔离、原文保存、重复保存不升版本、已有内容保护和编辑草稿保护。已备份并部署4个后端模块，保留远端已有模型日志增量，未推送。

真实 UniArt/Qwen：独立测试身份预置已生成的测试日记，完整聊天入口输入“我看了把日记保存一下吧。”，返回 HTTP200 / diary.save_draft / “2026-10-28 的日记已保存。”；数据库重新读取正文一致、revision=1，随后历史接口200。没有替用户原会话保存日记。

未收口问题：原用户历史读取当前正常返回20条；只重放模型请求也成功返回文字（HTTP200、finish_reason=stop）。未复现历史刷新失败与先前无效文本，不宣称已修复。未进行真实麦克风及WebRTC播放验收。

## 多轮写作修正计划

运行观察：重放用户失败请求，模型选择 diary.save_draft 并引用本会话“写刚才那张照片。”对应的文本结果。该结果标题为10月28日，用户此前明确提出写10月28号日记；服务端 diary_day 只识别标准写作指令，返回None，导致422。尚不能证明原始失败的模型参数与重放完全一致。

修正边界：保存工具增加结构化day字段；标准日记指令仍由服务端日期优先且检查一致。多轮写作允许模型从上下文确定日期并标注来源；日期不清楚先澄清，不由服务端猜。正文始终取已完成的同会话历史回复，来源须在保存请求之前，禁止提交正文或把保存回执当草稿。此处日记语义分类依赖模型，不能称为服务端证明。缺少日期、来源不可用改为明确的日记反馈，不映射成记忆错误。

### 多轮修正验收

已提交 d77fef41 并部署3个模块，31项相关测试通过。实现采用保存工具传入结构化day，正文仍从历史源记录读取；未增加独立草稿表。标准写作请求日期与工具day不一致时拒绝保存并提示核对，来源需早于保存回合。对于多轮来源是否属于日记，依赖模型语义判断，不能称为服务端强证明。

真实渠道使用独立测试身份，先确定2026-10-27日期，再生成“写刚才那张照片”的回复，输入“把刚写的日记保存。”：HTTP200、diary.save_draft、保存正文与源一致、revision1、历史接口200。没有执行用户原会话保存。缺少日期现在返回日记日期澄清文本。前端422通用记忆错误文案尚未修改；此项不能宣称完成。
