# s09：深度/姿态预处理与 H3 Ref2VA 工作流边界

日期：2026-10-17。范围：把用户提出的“原视频 + 人物图 → 可选 Depth Anything / DWPose / OpenPose → H3 Ref2VA → 24 fps 输出”与当前 iFrame/UniArt 链路和 s09 运行结果对照。公开 H3 提示词格式引用此前已核对的 [官方固定 commit 阅读记录](2026-10-16-h3-reference-generation-vs-video-editing-v1.md)；本轮没有新的网络读取或付费生成。

**用户澄清后的修正：**深度图和白模在拟议工作流中是先渲染成与源片同步的视频，再作为额外的 `<Video N>` **普通参考视频**发送，不主张使用专门的 `depth`/`pose`/ControlNet 参数。本文此前把“参考视频”和“硬控制字段”混为一谈；以下分别记录。

**生产就绪勘误：**目前没有经过 s09 验收、可稳定生产的深度视频或白模动作视频。因此 `<Video 2>/<Video 3>` 仅是未来输入设计，**不属于当前可执行或已准备提交的复刻链路**。存在白模 `.glb` 静态资产不等于存在与本片逐帧对齐的白模运动视频。

**四路线范围修正：**背景替换与人物/器械切割也没有通过 s09 的生产验收。绿底预览只是分割错误的可视化，不是已完成的背景替换。四条路线共用的最小试产与通过标准见 [四路线验证计划](2026-10-17-s09-four-auxiliary-video-production-validation-plan-v1.md)；在各自通过之前，本文的多视频参考只代表未来候选。

## Observed

- s09 源片 120 帧、30 fps、4 秒；正确目标人物图是 `枪法_4` 的 768 宽版本（SHA-256 `ba4e1a55…`）。B3R 已使用该图。输出 90 帧、24 fps、3.75 秒，人物仍主要为源片女性。[逐帧匹配](../raw/2026-10-11-qiangfa-cut-poc/s09-B3R-frame-match.json)显示输出 90/90 帧都与源片相同序号 ±1 帧最接近，导致源片后 30 帧（含前方展开与硬切）缺失。
- 当前 `src/models/uniart.py` 的视频请求 `content` 能发送文本、多个 `reference_image`、多个 `reference_video`、`reference_audio`，并传 `model/mode/duration/resolution/ratio/generate_audio/seed` 等字段。适配器可在**请求结构上**把 RGB 源视频、深度可视化视频、白模视频都列为 `reference_video`；`src/apps/recreation/service.py` 当前只把单个源片填入 `ref_video_urls`，因此产品工作流尚未接通后两路。当前路径也没有为 H3 发送 `depth`、`pose`、`ControlNet` 或输出 `fps` 的已实现字段。这是**iFrame 当前代码事实**，不是对所有 ComfyUI 节点或 H3 原厂能力的断言。
- 当前 H3 Ref2VA 六段提示词为 `subject_definitions`、`summary`、`retention_analysis`、`detailed_description`、`overall_soundscape`、`non_diegetic_music`。用户草案中的 `retained_elements` 可作为语义说明，但不是当前已核对的段名；保留关系应写在 `retention_analysis`。本地 `scripts/check_h3_prompt.py` 也按这六段检查。
- “H3 原生 24 fps”在本轮可直接确认的是**返回视频**为 24 fps；当前请求没有设置 `fps`。不能从返回媒体元数据推出模型内部固定帧率或 ComfyUI 节点配置要求。
- 现有 s09 mask 试验在深俯帧 45、转背帧 75、高举帧 84 等位置失败，枪杆/红缨又容易漏掉；前景实例分割只能作为待人工修正草稿。GVHMR/DPVO 分支对本片尚无已验收的相机轨迹或准确动作，因此没有可直接渲染成白模动作视频的可信运动轨。这些是当前原型的运行/审阅记录，不证明任何未来深度或白模方案必然失败。

## Direct implication

三路视频的拟议语义优先级是：`<Video 1>` RGB 原片决定本片可见事件、切点、枪端与人物和场景关系；`<Video 2>` 深度视频只补充相对前后层次；`<Video 3>` 白模视频只补充可复核的人体姿态/运动候选。后二者不能覆盖 RGB 原片中的可见事实，也不能被当作目标人物外观。三路必须先统一片段边界、时间基、帧位与左右方向；如果深度/白模对手和长枪不可靠，应显式保留这些区间为不确定，而不是让生成模型按错误控制片补全。

| 阶段 | 当前 s09 可执行做法 | 验收边界 |
|---|---|---|
| 素材冻结 | 固定 4 秒源片和 `枪法_4` 目标图的路径、哈希、帧率、时长 | 提交记录必须同时写明**预期目标图**和**实际上载图**的哈希；避免 A/B/B2/B3 的错误图重演 |
| 源视频分析 | 提取源帧证据表、动作相位、枪端、遮挡、切点；Depth Anything / DWPose / OpenPose 可提供额外观察与白模驱动候选 | 模型输出只能提候选；手、枪、红缨与快速边界须回到原帧复核；二维骨架不能代表枪的刚体几何 |
| 时间基准备 | 在本地先验证 30→24 fps 的事件映射；已有 96 帧/4 秒的模拟输入，前 90 帧覆盖源片完整事件 | 模拟只证明本地帧位；未证明 H3 会按该映射生成，也不能自行算作 H3 质量改善 |
| H3 请求（当前） | `<Picture 1>` 为目标人物，`<Video 1>` 为 RGB 源片；使用已核对的六段提示词 | 深度/白模视频目前没有合格产物，不能以空白、未复核渲染或低质代理片占据 `<Video 2>/<Video 3>` |
| H3 请求（未来候选） | 仅在独立质量闸门通过后，候选 `<Video 2>` 为同步深度视频、候选 `<Video 3>` 为同步白模视频，都按 `reference_video` 传递 | 当前适配器能组装多个参考视频，产品工作流只接一个；UniArt/H3 是否接受三个视频及是否正确绑定和利用，尚无运行证据。普通参考视频不等于硬控制 |
| 输出验收 | 先看人物替换、事件存在与顺序、帧对应，再看节奏、枪几何、背景/UI 杂质 | 若输出为源片同序号复制，应直接判身份/动作复刻失败；不得因“运镜保真”掩盖主体没有替换 |

## Not yet proven / Hypotheses

- 深度视频与白模视频作为附加 `reference_video` 能被 UniArt/H3 接受、被正确排序绑定为 `<Video 2>/<Video 3>`，并改善动作/空间保真：**未验证**。这与专门的深度/骨架硬控制能力是不同命题。白模本身若来自不准确的人体恢复，也可能把错误带入提示与参考。
- “H3 对 V2V 动作迁移支持极好、直接丢原视频即可高保真换人”：属于外部性能主张，本片正确目标图的 B3R 结果不支持把它当作当前链路的已验证能力。
- ComfyUI 比官方 API 更适合本任务，或允许设置 H3 内部/输出 fps：未核对具体节点和后端参数。
- 源视频 30 fps 与输出 24 fps 的同序号映射发生在模型、UniArt 预处理或结果编码的哪一层：未定位。

## What would verify it

1. **当前 RGB 主线独立推进：**对本地 24 fps 时间基模拟做输出验证时，冻结正确人物图、B3 提示词和 seed；只改变源视频时间基，检查是否仍出现同序号近复制、是否覆盖源片帧 99–119、身份是否替换。该步会产生新的付费任务，须单独授权。它不依赖深度或白模候选完成。
2. **深度视频生产闸门：**先在 s09 源帧 45、69–87、99–112 等高风险区间试产，输出与 RGB 帧号一一对应、切点不跨帧平滑的深度序列；人工检查躯干、手、枪杆、红缨、遮挡前后关系和正常速闪烁。对无法分辨或明显错误区间标 `unknown/reject`，不能默默补值。通过后才能编码为参考视频候选。
3. **白模视频生产闸门：**先有已复核的人体姿态、动态相机轨迹、根运动和人体/枪握点关系，再把白模动画渲染到与 RGB 相同机位、帧率和切点。逐段检查深俯、高举、回落、前伸及切后视角；GVHMR 或分割输出有误的区间保留人工修订/拒绝状态。静态 `.glb` 或一段看似流畅的动画不足以通过。
4. 只有上述候选分别通过，才核对 UniArt/H3 多视频参考上限、列表顺序与 `<Video N>` 绑定规则，并固定 RGB 源片与人物图，先加一路深度视频，再另试白模视频。验收附加视频的实际贡献和外观污染风险；在此之前不扩展产品生成请求。
